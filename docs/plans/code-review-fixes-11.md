# Исправления по этапу 11 ревью — REST-адаптеры

**Основание:** находки [`docs/review/11-rest.md`](../review/11-rest.md);
порядок работы — как в планах этапов 1–10 (владелец 2026-10-21: «если есть изменения — сразу исправь»).

Каждая задача — проверка в сборке или тест, прогон на старом коде (обязан упасть),
перенос всех мест, `./mvnw -P '!frontend' install` зелёный, один коммит.

## Порядок

Сначала то, как отказ доходит до клиента: последняя линия обработчика (1) — после неё ни один отказ
не уходит без кода; затем `detail` без имён классов (2) и заголовки на языке запроса (3). Bean Validation (4)
опирается на обработчик из (1)–(3). Переводы в мапперы (5) — после (4): ручные проверки из контроллеров
к тому времени ушли. Дальше мелкое — `Location` (6), срок потока (7); пагинация версий (8) меняет порт
хранения; сверка контракта (9) — последней, когда пути и параметры уже не меняются.

## Расхождения плана с фактом

- **Задача 1.** У обработчиков контекстов и общего был один порядок по умолчанию (`LOWEST_PRECEDENCE`):
  пока их исключения не пересекались, это не мешало, но перехват `Exception` в общем обработчике
  при равном порядке мог встать раньше контекстных и съесть их отказы. Обработчикам контекстов дан
  явный `HIGHEST_PRECEDENCE`. Отказы Spring Security (`InsufficientAuthenticationException` из
  резолвера текущего пользователя) последняя линия бросает дальше — иначе `401` стал бы `500`;
  случай `ProblemFallbackIT#unauthenticatedStays401` проверяет только цепочку фильтров: путь через резолвер
  в тестах не воспроизводится — фильтр отказывает раньше. Испорченная форма `multipart` ушла
  в `400 BAD_REQUEST`: в MockMvc её не воспроизвести — форму там не разбирает Tomcat. На старом коде
  три случая из четырёх падали: `405` и `415` без тела, сбой — исключением мимо обработчика.
- **Задача 2.** Путь поля берётся из цепочки `JacksonException.getPath()` (имена свойств и индексы),
  а не из `getPathReference()`: тот начинается с имени класса записи (`CreateModelRequest["workspaceId"]`).
  Тело, не разобранное как JSON вовсе, — «тело запроса не разобрано» без пути. Текст Spring и парсера
  пишется в журнал уровнем `DEBUG`. На старом коде оба новых случая падали с типами Java в `detail`.
- **Задача 3.** Заголовок modeling выбирается по классу отказа, а не по статусу: перечисление закрытое,
  и `500` дефекта снимка больше не уходит английской фразой HTTP. Ключ `modeling.problem.bad-request`
  удалён — `400` modeling не отдаёт. У interchange один заголовок «Импорт и экспорт» на все статусы
  заменён ключом на статус, `400` по-прежнему «Некорректный файл». В тесте interchange проверен `404`
  отсутствующей привязки, а не `409` из плана: `404` получается без подготовки данных. У отказа самого
  Spring MVC со статусом `400` (нет заголовка, не тот параметр) код — `BAD_REQUEST`, а не
  `REQUEST_NOT_SUPPORTED`. На старом коде заголовок `400` был «Bad Request» при любом языке.
- **Задача 4, расхождение с находкой.** Аннотации поставлены не на все поля из `required` контрактов,
  а только там, где REST-слой сам проверял руками или падал: элементы списков, ключ свойства, концы
  ребра и связи, папка, идентификаторы раскладки, модель помощника, выключатель. Имя, тип, ссылка Git,
  описание плана проверяют сценарий и домен со своими кодами — дубль аннотацией сменил бы код отказа
  и нарушил бы «каждая проверка на своём уровне» (§4.2.1). Ручные `require`, `items`, проверки полей
  авторазметки и `model(...)` помощника из контроллеров ушли; ключ `modeling.request.items-empty`
  удалён — пустой список теперь «не задано поле itemIds».
- **Задача 4.** Отказ формы переводит общий обработчик, а не обработчики контекстов: он один видит оба
  исключения Spring (`MethodArgumentNotValidException` у тела-объекта, `HandlerMethodValidationException`
  у тела-массива `List<@NotNull @Valid …>` списка доступа), а код и текст берёт по пакету класса
  обработчика (`FormRefusal`) — тот же `MDL_INVALID_INPUT`, `IXC_INVALID_REQUEST`, `ADV_INVALID_INPUT`,
  что у ручного отказа контекста. Обработчики контекстов сузить по пакету нельзя: отказ modeling
  приходит и из контроллеров interchange. На старом коде три случая из пяти отвечали `500`, свойство без
  ключа на несуществующем элементе — `404` (до домена не доходило), помощник без модели проходил:
  его проверял контроллер.
- **Задача 5.** Правило запрещает контроллеру конструкторы трёх видов: DTO REST-слоя, значения
  `application.dto` (`PropertyValue`, `StyleValue`, `BendpointValue`) и вложенные типы команд и запросов
  (`ReplaceAccessListCommand.Entry`, `SaveViewLayoutCommand.NodeBounds`). Сами команды и запросы
  (`new GetModelQuery(id)`) контроллер собирает по-прежнему — это разбор запроса, как в примере §3.3.8.2.
  На старом коде — 15 нарушений в пяти контроллерах трёх контекстов и в `SessionController` bootstrap.
  `SessionController` правилом не охвачен: его DTO лежат в `bootstrap.security.dto`, а сам он разбирает
  токен — это предмет этапа 12 (безопасность), там и решится, нужен ли ему маппер. Modeling `DtoMapper`
  переводит теперь в обе стороны; у interchange для импорта — `InterchangeDtoMapper` рядом с `GitDtoMapper`.
- **Задача 6.** Проверка — в `ClientIdsIT`, а не в `ViewEditingIT` и `ModelLifecycleIT` из плана: папку
  и ребро с заданным клиентом идентификатором создаёт именно он, и адрес сверяется с этим идентификатором.
  Адрес папки — `/models/{id}/tree/{folderId}`: отдельного ресурса папки в API нет, а этот адрес её
  переименовывает. На старом коде оба `201` шли без `Location`.
- **Задача 7.** `SseEmitter` без срока берёт срок асинхронного запроса Spring MVC — `spring.mvc.async.request-timeout`;
  комментарий к настройке говорит, что это и срок потока. Тест — в `archi-bootstrap`: у модулей
  `*-adapter-rest` своих тестов нет. На старом коде срок эмиттера был `330000`.
