# Отступления от стандарта кода: ADR-0021…ADR-0026 в коде и сборке

**Откуда:** этап 0 ревью кода ([`code-review.md`](code-review.md)), 2026-10-14. Владелец
выбрал записать расхождения с `java-spring-code-guidelines-v2.md` решениями, а не
переделывать код. Решения — [`ADR-0021`](../../spec/adr/0021-source-style.md)…
[`ADR-0026`](../../spec/adr/0026-config-values-in-yaml.md), в регистре помечены полем
`deviates_from`.

**Зачем план.** ADR записывает решение, но не держит его. В разделе «Последствия» у каждого
есть что-то, что надо сделать: проверка в сборке, правка контракта, перенос кода.
Без этого решение живёт договорённостью и тихо нарушается при первой правке.

**Чего план не делает:** не исправляет нарушения стандарта, оставшиеся в силе (покрытие
Javadoc, JSpecify, `proxyBeanMethods`, пагинация, JaCoCo — D-02, D-14…D-17). Они —
находки ревью и уйдут в план исправлений после этапа 18.

**Порядок внутри задачи** — по глобальному правилу: сначала проверка в сборке, её прогон
на нынешнем коде (проверка обязана упасть на известном нарушении, а если нарушений нет —
на нарочно испорченном примере, который затем удаляется), потом перенос всех мест.
Задача — один коммит.

## Решения, нужные от владельца

- [x] **Р-1. События вне агрегата** (`ADR-0023`). ADR говорит «событие создаёт
      бизнес-метод агрегата», а в коде два исключения: `VersionService:102` создаёт
      `ModelVersionCommitted`, `GitPublishingService:383` — `GitSnapshotCommitted`.
      Варианты: **(а)** перенести создание в агрегат — `ModelVersion` при фиксации
      и `GitBinding` при записи коммита; **(б)** уточнить ADR: событие, у которого нет
      одного агрегата-владельца, создаёт application-сервис. **Рекомендация — (а)** для
      `ModelVersionCommitted`: это звено outbox (`ADR-0003`), его потеря — молчаливая
      дыра в журнале Git, ровно риск, ради которого стандарт ввёл правило. Для
      `GitSnapshotCommitted` — решить по коду задачи 6.

      **Решено 2026-10-14 — смешанно.** `ModelVersionCommitted` создаёт `ModelVersion.next`
      и возвращает вместе с версией. `GitSnapshotCommitted` остаётся в сервисе: это факт
      внешней системы (коммит в Git состоялся), а не переход агрегата, и публикуется
      даже без записи привязки. Исключение записано в `ADR-0023` (редакция 1.1).
- [x] **Р-2. Пул соединений interchange** (`ADR-0026`). `spec/nfr/interchange.yaml` требует
      отдельный пул (8 соединений, таймаут запроса 120 с), приложение работает на общем
      (20 и 15 с). Варианты: **(а)** второй пул; **(б)** править спеку. **Рекомендация —
      (б):** импорт пишет таблицы modeling внутри транзакции `UnitOfWork` modeling
      (`ADR-0024`) — второй пул разорвал бы её на две; защиту канвы от длинного импорта
      дать ограничением одновременных импортов, а таймаут запроса импорта поднять
      точечно, а не на весь пул.

      **Решено 2026-10-14 — (б) с пределом импортов:** правится `spec/nfr/interchange.yaml`,
      заводится предел одновременных импортов и точечный таймаут запроса импорта.
      Записано в `ADR-0026` (редакция 1.1).

## Задачи

### ADR-0021 — стиль исходников

- [x] **1. `.editorconfig`.** UTF-8, LF, без табуляций; Java — отступ 4, `max_line_length = 120`.
      Остальные типы файлов — по тому, как они написаны сейчас (проверить фронтенд, YAML,
      SQL, XML), а не по Java.
      Сделано: Java, XML, SQL, Python — 4; TS, CSS, JSON, YAML — 2; эталоны и фикстуры
      (`*.archimate`, `fixtures/`, `export-parity/`, `*-snapshots/`) исключены целиком —
      там нет перевода строки в конце, и редактор не должен его добавлять.
- [x] **2. Длина строки и табуляция в сборке** вместе с правкой 59 строк длиннее 120
      (35 файлов). Checkstyle (`LineLength` 120, `FileTabCharacter`) в `pluginManagement`
      родителя, фаза `validate`, нарушение роняет сборку; версия пинится. Сначала прогон
      без правок — ждём ровно 59 нарушений, — затем правка и зелёная сборка в одном
      коммите. Импорты и `package-info` Checkstyle не трогает: их правила — этап 1 ревью.
      Сделано: `config/checkstyle.xml` (Checkstyle 14.3.0, проверки по тексту без разбора
      Java). Прогон до правки — 125 нарушений: в плане было 59, тесты не считались, а предел
      ADR касается и их. Перенесено 104 строки (два субагента, дифф сверен: меняются только
      пробелы и переводы строк, разрезанные литералы склеиваются в прежний текст, текстовые
      блоки не тронуты). 21 строка разметки XML в текстовых блоках оставлена — эталоны
      в раскладке Archi; их пропускает `ignorePattern`, исключение записано в `ADR-0021` 1.1.

### ADR-0022 — контракт ошибок

- [x] **3. `X-Trace-Id` в контрактах.** Заголовок отдаётся на каждом ответе
      (`RequestCorrelationFilter`), но ни в одном из трёх `spec/contracts/*/rest-api.openapi.yaml`
      не описан. Завести общий `components.headers.XTraceId` и сослаться на него
      из ответов `Problem` и успешных; `docs/backend.md` §8.1 — RFC 9457 вместо 7807,
      строка о заголовке.
      Сделано: заголовок у всех ответов трёх контрактов (у ответов-ссылок — через
      `components.responses`), формат — 32 hex, как его порождает фильтр. Попутно
      исправлен скрытый дефект: 14 однострочных ответов `{ description: …, … }` YAML
      читал обрезанными по первой запятой («Модель в DELETED» вместо полной фразы) —
      развёрнуты в блок.
- [x] **4. Тест на заголовок.** Интеграционный: `X-Trace-Id` есть на успешном ответе
      и на `problem+json`, совпадает с `traceparent`, если тот пришёл. Сначала поискать
      существующий (`grep X-Trace-Id` в тестах) — если есть, задача сводится к проверке
      покрытия обоих случаев.
      Сделано: успешный ответ с `traceparent` уже проверял `ObservabilityIT`; добавлен
      `problemCarriesGeneratedTraceId` — `404 problem+json` без `traceparent` несёт новый
      `X-Trace-Id` из 32 hex.

Ответ на **неожиданное** исключение (нет общего `@ExceptionHandler`) проверяет этап 11
ревью — в этот план не входит.

### ADR-0023 — события создаёт агрегат

- [x] **5. Проверка в сборке.** ArchUnit в `archi-bootstrap/.../architecture/`:
      конструкторы реализаций `DomainEvent` вызываются только из классов
      `..domain..` своего контекста. У interchange маркера нет — завести
      `interchange.domain.common.DomainEvent` и пометить им события контекста
      (`GitSnapshotCommitted`, `ImportApplied`). Прогон на нынешнем коде обязан упасть
      на `VersionService` и `GitPublishingService`. `GitSnapshotCommitted` — в исключениях
      поимённо с причиной (Р-1); после этого проверка падает только на `VersionService`.
      Коммит — проверка вместе с задачей 6, иначе сборка красная.
- [x] **6. `ModelVersionCommitted` создаёт агрегат.** `ModelVersion.next` возвращает версию
      вместе с событием (по образцу `Created<ViewNode>`); данные, которых у версии нет
      (`workspaceId`, число элементов и связей), — аргументами. `VersionService` публикует
      полученное событие, сам его не собирает. Юнит-тест `ModelVersion` на событие; публикация
      прежняя — в outbox той же транзакцией, `GitExportIT` и round-trip зелёные.
      Сделано: `ModelVersion.next` заменена на `commit`, возвращающую `Committed(version, event)`
      (образец `Created<ViewNode>` из плана не подошёл — это признак «создан или был», а не
      носитель события); размер модели — `ModelVersion.ModelSize`. Маркер `DomainEvent`
      заведён в interchange. `DomainEventOriginTest` на старом коде падал ровно на
      `VersionService:104`. Юнит-тесты (461), `Git*IT`, `MergeRequestIT`,
      `SnapshotRetentionIT`, `RoundTripApiIT` зелёные.

### ADR-0024 — транзакция портом

- [x] **7. Проверка в сборке.** Enforcer держит только `domain` и `application`. ArchUnit
      на все модули: нет `org.springframework.transaction.annotation.Transactional`
      и `jakarta.transaction.Transactional`; `TransactionTemplate`
      и `PlatformTransactionManager` — только в `bootstrap.wiring`. Нарушений сейчас нет:
      проверку доказать на временном классе с `@Transactional`, затем его удалить.
      Сделано: `TransactionBoundaryTest` — нет `@Transactional` (Spring и Jakarta) ни на классе,
      ни на методе; пакеты `org.springframework.transaction..` и `jakarta.transaction..` —
      только в `bootstrap.wiring`. Временный класс в `bootstrap.web` ронял оба правила.
- [x] **8. Ссылка в `CLAUDE.md`.** Абзац «Application-слои без Spring: транзакция —
      порт `UnitOfWork`…» получает ссылку на `ADR-0024`, как у остальных решений; текст
      не дублируется.

### ADR-0025 — Logback и ECS

- [x] **9. Один бэкенд логов.** Правило enforcer `bannedDependencies` в `archi-bootstrap`:
      `org.apache.logging.log4j:log4j-core` и `spring-boot-starter-log4j2` запрещены —
      два бэкенда на classpath SLF4J разрешает предупреждением и молча выбирает один.
      Проверку доказать временной зависимостью.
      Сделано: исполнение `single-logging-backend` в `archi-bootstrap`; унаследованный
      из родителя запрет Spring (`ban-framework`) там выключен — иначе он ронял бы модуль,
      которому Spring нужен. С временной `log4j-core` сборка падала на `validate`.

Пересмотр решения — когда логи начнёт собирать общая платформа банка; задачи на это нет.

### ADR-0026 — значения требований в YAML

- [x] **10. Имя пространства по умолчанию — ключ локали.** `archi.modeling.default-workspace-name`
      (русский текст в YAML) → ключ в `messages*.properties`, текст через `TextCatalog`
      на языке по умолчанию (на старте запроса нет). Это данные: имя пишется в базу один
      раз, у существующих баз не меняется. `tools/check-string-literals.py` YAML
      не проверяет — расширить его на `application*.yaml` (кириллица в значениях)
      и прогнать до правки.
      Сделано: `check-string-literals.py` проверяет значения `application*.yaml` и до правки
      падал ровно на `default-workspace-name`. Имя — ключ `modeling.workspace.default-name`;
      умолчание решает `WorkspaceService.ensureDefault(Optional<String>)` через `TextCatalog`.
      Расхождение с планом: имя осталось настраиваемым — прежде оно было записано как данные
      установки, поэтому стало переменной `ARCHI_DEFAULT_WORKSPACE_NAME` (по `ADR-0026` —
      значение стенда), а не исчезло. Язык на старте — `spring.web.locale`: запроса нет,
      а системная локаль сервера не в счёт; `DefaultWorkspaceIT` зелёный и в JVM с `en`.
- [x] **11. Пул interchange по Р-2.** `spec/nfr/interchange.yaml`: `storage` — общий пул
      приложения (20, 15 с) вместо отдельного, с причиной; новое требование — предел
      одновременных импортов и таймаут запроса импорта (`timeout` у сценария импорта уже
      120 с). В коде: предел — в `ImportService` (отказ сверх предела — код из `InterchangeCodes`,
      ключ в обеих локалях, строка в контракте), таймаут — на запросах применения импорта.
      Правка требований — `tools/render-requirements-index.py`, если затронут реестр.
      Сделано, с двумя расхождениями с планом. **Предел импортов не новое требование:**
      `concurrency.max_parallel_imports_per_workspace: 1` в спеке уже был, но в коде
      не исполнялся — реализован он (`ImportGate`, отказ `409 IXC_IMPORT_BUSY` сразу,
      без ожидания). Рядом не исполняется и `max_parallel_export_jobs: 4` — находка
      для ревью, в этот план не входит. **Точечный таймаут не понадобился:** таймаут
      запроса — подсказка JPA для запросов, а запись документа идёт вставками при сбросе
      транзакции; импорт референсной модели и `LoadProfileIT` проходят с общими 15 с.
      Реестр требований не затронут.
- [x] **12. Сверка YAML со `spec/nfr/`** — `tools/check-nfr-config.py`: закрытая таблица
      «ключ `application.yaml` ↔ путь в `spec/nfr/<bc>.yaml`» (пул, таймаут запроса,
      частота и контекст помощника, срок блокировки), гейт в работе `spec` CI. До задачи 11
      проверка обязана упасть на пуле interchange; после — зелёная. Скрипт — в список
      `tools/` в `CLAUDE.md`.
      Сделано: 14 пар и отметка «пул общий»; гейт в работе `spec` CI. Задача 11 закрыта
      раньше, поэтому падение доказано на версии `spec/nfr/interchange.yaml` до неё — ровно
      два расхождения пула. Срок блокировки в пары не вошёл: в `spec/nfr` его нет.

## Отменённые варианты

- **Таблица отступлений в `CLAUDE.md`** (была 2026-10-14, убрана тем же днём). Вторая
  копия регистра решений, а регистр по правилу проекта один и третьей копии не допускает.
  Отступления помечены полем `deviates_from` в `decisions.yaml`.
- **Проверка ArchUnit на отступ и длину строки.** ArchUnit читает байткод, форматирования
  в нём нет; это работа Checkstyle.

## Расхождения плана с фактом

- **2026-10-14, при составлении.** `ADR-0022` и отчёт этапа 0 утверждали, что `traceId`
  есть в теле ошибки. Неверно: он идёт заголовком `X-Trace-Id`. Исправлено
  в `ADR-0022` и `docs/review/00-podgotovka.md` (`24bf21a`); отсюда задачи 3–4.
- **2026-10-14, при составлении.** `ADR-0023` записан как «события создаёт агрегат»,
  а в коде два события создают application-сервисы. ADR опирался на `pullEvents()`
  у агрегатов и не проверил создание событий вне них; отсюда Р-1 и задачи 5–6.
