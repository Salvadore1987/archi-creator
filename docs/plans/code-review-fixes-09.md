порядок работы — как в планах этапов 1–8 (владелец 2026-10-21: «если есть изменения — сразу исправь»).

Каждая задача — проверка в сборке или тест, прогон на старом коде (обязан упасть),
перенос всех мест, `./mvnw -P '!frontend' install` зелёный, один коммит.

## Порядок

Сначала запрет сборки (1), затем деньги: двойной поток и недосписание (2, 3), транзакции и метрики (4),
детали отказа при повторе (5), мелочи (6). Перевод на входные порты и handler'ы (7) — по уже
исправленному коду.

## Расхождения плана с фактом

- **Задача 2.** Ключ занимается блокировкой `pg_advisory_xact_lock` по автору и ключу, затем чтением
  и обычной записью JPA, а не `INSERT … ON CONFLICT DO NOTHING`, как предлагала находка: в нативной
  вставке Hibernate привязывает `null` (у сессии без представления — `view_id`) как `bytea`, и столбец
  `uuid` его не принимает. Уникальность ключа в схеме остаётся последней защитой. Занявший ключ
  параллельно отвечает так же, как повтор: `409 SESSION_IN_PROGRESS`, конфликт параметров или результат.
- **Задача 2, отменённый вариант.** Интеграционный тест «четыре параллельных `POST /ai/review` с одним
  ключом» на старом коде проходил (`[200, 409, 409, 409]`): обращения через MockMvc фактически
  упорядочены, гонка не воспроизводится. Гонку держат юнит-тест (параллельное занятие во время чтения
  модели) и `AdvisorSessionClaimIT` — две транзакции на настоящем Postgres; без блокировки второй
  падает `DataIntegrityViolationException` на `uq_advisor_session_key`.
- **Задача 3, расхождение с находкой.** Дефект шире записанного в 09-03. Обрезанный сервером поток
  и поток, отменённый новым обращением, у SDK кончаются **молча** — итератор просто заканчивается.
  Сценарий принимал это за конец ответа: сессия `COMPLETED` с частью текста и выходом из `message_start`
  (единицы токенов). Теперь поток без `message_stop` — обрыв: `LlmUnavailableException`, сессия `FAILED`,
  выход — не меньше оценки по пришедшим символам текста и входа инструментов. Оценка — одно правило
  домена `TokenUsage.estimate` (4 символа на токен, вверх), им же считает размер `ModelContext`.
- **Задача 4.** Фейк `UnitOfWork` в `Fixture` теперь нумерует транзакции и роняет вложенную: на старом
  коде падали 12 тестов сценария (каждое списание расхода читало настройки вложенной транзакцией).
  Проверка общая для всех тестов помощника, а не одного случая.
- **Задача 5.** Отказ по частоте при повторе остаётся отказом, даже если окно уже освободилось:
  повтор ключа отдаёт результат сессии, а результат отклонённой — отказ (новый запрос — новый ключ).
  Ожидание при повторе — остаток минуты от обращения, не меньше секунды; держать отказ «вечным»
  без ожидания значило бы снова отдавать `Retry-After` без числа.
