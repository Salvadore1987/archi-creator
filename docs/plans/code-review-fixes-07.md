# Исправления по этапу 7 ревью — application interchange: SVG, PNG, OEF

**Основание:** находки [`docs/review/07-svg-png-oef.md`](../review/07-svg-png-oef.md);
порядок работы — как в планах этапов 1–6 (владелец 2026-10-21: «нужно сразу исправить»).

Каждая задача — проверка в сборке или тест, прогон на старом коде (обязан упасть),
перенос всех мест, `./mvnw -P '!frontend' install` зелёный, один коммит. Задачи, задевающие
писатели, дополнительно проходят эталоны: `ExportParityFixturesTest` и `OefExportFixturesTest`.
Эталон меняется только там, где правка меняет поведение намеренно, — это записывается
в «Расхождениях»; у рефакторинга эталоны совпадают байт в байт.

## Порядок

Сначала поведение: падение OEF и крепление связи к связи — одна функция в `Routing`, она же
убирает вложенный `computeIfAbsent` (задача 1), затем внедрение разметки в SVG (2). Дальше —
правила в одном месте (3–5), рефакторинг писателей по уже исправленному коду (6),
мелочи (7–8). Тесты 07-10 идут в задачи, которые закрывают их случаи; остаток — задача 9.

## Расхождения плана с фактом

- **Задача 1, ошибка по ходу.** Первая версия `Routing.endpoint` принимала
  `Function<String, Optional<Rect>>` — тот же `Optional` в параметре, только отложенный.
  `CodingRulesTest` её пропустил: проверял сырой тип параметра (`Function`), а не аргументы
  дженерика. Владелец заметил 2026-10-21. Лечение — задача 0: правило смотрит и аргументы
  дженериков параметров и полей; на старом коде оно нашло ещё `DocumentAssembler`
  (`Map<String, Optional<String>>` в четырёх методах — теперь `null` значит «типизирован,
  значения нет», `containsKey` по-прежнему отличает его от нетипизированного). `Routing.endpoint`
  принимает карты фигур и связей. Возврат `Optional<Rect>` остаётся: это результат поиска конца.
- **Задача 1.** Эталоны OEF и сверки SVG не изменились: в фикстурах нет связи к связи с точками
  перегиба, где OEF раньше считал крепление между центрами. Конец, не найденный на представлении
  (цикл или цепочка длиннее 8 звеньев, как у канвы), раньше молча давал точку (0, 0) — теперь линия
  без точек перегиба и запись отчёта `bendpoint` (ключ `interchange.oef.loss-bendpoints`).

- **Задача 2.** Тест на старом коде воспроизвёл внедрение: `<script` в выводе. Неверный цвет
  узла или ребра теперь — токен слоя и запись отчёта `style` (ключ `interchange.image.loss-style`);
  иконка красится экранированным значением, Batik — с явным `KEY_ALLOW_EXTERNAL_RESOURCES=false`.
  Эталоны сверки не изменились.

- **Задача 5, неточность ревью.** В 07-07 было «те же числа — второй раз в CSS канвы» со ссылкой
  на `canvas.css:234, 256, 394` — это кегли интерфейса (выбор связи, масштаб), а не подписей.
  Канва уже брала кегли и высоты строк подписей из токенов; числами в CSS были только начертания
  ярлыка группы (600) и заметки (400) и разрядка ярлыка (0.04em). Находка в файле ревью поправлена.
  Сделано: писатель читает `node_font`, `node_font_weight`, `node_subtitle`, `edge_label_font`;
  три числа стали токенами `group_tab_font_weight`, `group_tab_letter_spacing`, `note_font_weight`
  (спека токенов 1.1) и для CSS, и для писателя. `normal`/`bold` (400/700) остались константами
  писателя — это значения сокращённой записи `font` CSS, а не стиль. Эталоны сверки — байт в байт,
  `visual/` Playwright — 11 из 11.

- **Задача 6.** `SvgWriter.label` — выбор оформления (`tabTypography`, `nameTypography` → запись
  `Typography`), подзаголовок, выравнивание, вылет за бока и обрезка — отдельными методами;
  накопление `lineTop` оставлено сложением, а не умножением, чтобы не сдвинуть байты.
  `OefWriter` (1017 строк) разрезан на `OefWriter` (концепты и папки, 330), `OefViews`
  (представления, 405), `OefStyle` (135), `OefPass` (общее состояние и отчёт, 175) и `OefMarkup`
  (разметка и числа, 110). Разрез сделан скриптом, и он сначала вписал `pass.` внутрь литерала
  `<diagrams>` — исправлено до прогона; урок: замена имён по регулярному выражению не отличает
  код от строк, после неё литералы проверяются отдельно. Эталоны OEF и SVG — байт в байт.

- **Задача 7.** Отдельной проверки в сборке нет: незакрытый поток ресурса машинно не ловится
  без своего загрузчика классов в тесте — несоразмерно правке. Защита — устройство: ни `OefSchema`,
  ни `Input` потоков больше не открывают, разборщик открывает и закрывает их по `systemId`.

- **Задача 8.** Вид объекта представления — `DocumentNode.viewObject()`. По ходу нашёлся обход
  правила 06-08: `OefWriter` проверял «связь ли элемент фигуры» окончанием `xsi:type` через константу,
  а шаблон `DocumentKindRuleTest` видит только литерал. Заменено на `kind() != RELATIONSHIP`;
  шаблон не расширен — константа в регулярном выражении ловится только поимённо, а единственная
  оставшаяся (`OefWriter.RELATIONSHIP_SUFFIX`) не классифицирует, а выводит имя типа OEF из имени
  Archi у уже отобранной доменом связи. Локаль `ru` — одна, `LabelLayout.RUSSIAN`; условие
  непрозрачности в `ViewScene` — со скобками.

## Отменённые варианты

- **Отдельный тест на закрытие потоков `OefSchema`** (задача 7) — нужен свой загрузчик классов
  с подсчётом потоков; правку держит устройство: потоков код больше не открывает.
- **Шаблон `DocumentKindRuleTest` на константы с окончанием типа** (задача 8) — регулярное выражение
  поймало бы их только поимённо; единственная оставшаяся константа не классифицирует узел.
