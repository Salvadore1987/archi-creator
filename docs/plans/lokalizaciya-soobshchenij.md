# Локализация сообщений сервера и строковые литералы

## Контекст

Ревью `InterchangeController` (2026-10-09): `detail` и `title` ответов `problem+json`
собраны из русских строк прямо в коде, а в части строк — ссылки на спецификацию
(`(FR-50)`, `(FR-49)`, префиксы `INV-MDL-008: …` в тексте). Так интерфейс нельзя
перевести, а ссылка на документ разработки уходит пользователю. Проверка всего кода
нашла около 350 русских литералов в 95 файлах всех слоёв и около 50 строк с якорями.

Правило проекта уже требовало строк в ресурсах (NFR-08, `UI-021`), но держалось
только во фронтенде: на сервере проверки не было, и код этапов 1–3 его нарушал.

## Решения

- **Текст — в `i18n/messages*.properties`, в коде — ключ и аргументы.** Исключение
  несёт `Message(key, args)` вместо текста; аргумент сам может быть `Message`
  (название объекта: «модели», «папки»). Текст собирает `MessageSource` по локали
  запроса: русский по умолчанию, английский — второй язык, чтобы перевод был
  проверяемым, а не обещанием.
- **Домен и application — без Spring.** У каждого контекста свой `Message` (modeling-domain,
  interchange-domain): модули контекстов друг от друга не зависят. Текст, который
  сервер сохраняет как данные (комментарий версии, находка импорта, «да/нет» в CSV),
  собирается через порт application-слоя, реализованный в `archi-bootstrap`
  на `MessageSource`.
- **Коды ошибок — константы в классах `*Codes`.** Код инварианта в поле `code` —
  контракт API и остаётся; в тексте сообщения якорей нет.
- **Ключи — константы в классах `*Messages`**, у каждого контекста свой. Ключ
  вида `modeling.model.not-found`.
- **Проверка сборкой:** `tools/check-string-literals.py` (русский литерал, литерал
  с якорем вне `*Codes`, исключение с текстом-литералом — отказ) в работе `spec` CI;
  `MessageBundlesTest` — каждый ключ из `*Messages` есть во всех локалях, число
  подстановок совпадает, в текстах нет якорей. Во фронтенде статическая проверка
  расширяется с JSX на все `.ts`/`.tsx`.

## Журнал

<!-- Расхождения с планом, найденные дефекты, отменённые варианты. -->

- **2026-10-09. Четыре задачи сервера — одним коммитом.** Инфраструктура, modeling,
  interchange и `archi-bootstrap` связаны компиляцией: у `ModelingKernel`, `ImportService`
  и `ExportService` появился порт `TextCatalog`, а его реализацию и проводку даёт
  `archi-bootstrap`. Порознь модули не собирались бы, поэтому коммит один.
- **2026-10-09. `ModelingText` в REST modeling отменён.** Первая версия держала
  переводчик сообщений в адаптере; он дублировал реализацию порта `TextCatalog`
  в `archi-bootstrap` (`MessageSourceTexts`, одна на оба контекста). Адаптеры
  REST обоих контекстов берут текст через порт.
- **2026-10-09. Находки импорта хранятся текстом.** Находка несёт `Message`; при записи
  адаптер хранения собирает текст на языке запроса, в котором прошёл импорт, —
  это отчёт, а не сообщение. Прочитанная из базы находка оборачивается ключом
  `interchange.stored-text` (`{0}`) и выводится как есть.
- **2026-10-09. Ловушка: ведущий пробел в `.properties`.** Загрузчик срезает пробел
  в начале значения; у частей сообщения « (строка {0})» и « и ещё {0}» он значим —
  экранируется обратной косой чертой. Текстов с апострофом нет: при
  `always-use-message-format` апостроф в `MessageFormat` — служебный символ.
- **2026-10-09. Имя пространства по умолчанию — конфигурация, а не текст кода.**
  `@DefaultValue` с русским именем убран из `ModelingSettings`: значение задаёт
  `application.yaml`, это данные, которые админ может поменять, а не строка интерфейса.
- **2026-10-09. Язык ответа — из `Accept-Language`, по умолчанию русский.** Системная
  локаль сервера на выбор не влияет (`fallback-to-system-locale: false`).
