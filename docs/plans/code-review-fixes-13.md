## Расхождения плана с фактом

- **Задача 1.** Числа Git (`timeout`, `retry-base`, `retry-max`) жили только умолчаниями записи `GitSettings`;
  по `ADR-0026` они вынесены в `application.yaml` — иначе сверять было бы не с чем. На старом коде сверка
  падала трижды: настроек в YAML не было. Повтор Git без джиттера записан в спеку с причиной — очередь
  проходит один планировщик. Вне объёма: `spec/nfr/modeling.yaml` `keycloak_jwks` тоже обещает предохранитель
  и повторы, которых у декодера JWT Spring Security нет, — это граница безопасности, этап 14.
- **Задача 2.** Предел соединения — 10 s, число записано в `spec/nfr/advisor.yaml` (`connect_timeout`)
  и сверяется. Таймаут чтения не задан отдельно: у SDK он равен пределу вызова, и для потока это предел
  паузы между кадрами. На старом коде сверка падала: настройки не было.
- **Задача 3.** Предохранитель — Resilience4j 2.4.0 (`resilience4j-circuitbreaker`, метрики —
  `resilience4j-micrometer` без модулей повтора, лимита и переборки). Аннотаций нет: исход потока известен
  не по возврату метода, а по концу чтения, поэтому разрешение берётся программно, а исход — ровно один:
  целый поток — успех, отказ API и обрыв — неудача, отмена клиентом — разрешение возвращается.
  Длительность — время до открытия потока: длинный ответ модели не «медленный вызов». Доля медленных
  открытий — та же, что доля отказов (в спеке была только граница медленного). Оценка — когда окно
  заполнено (`minimumNumberOfCalls` = размер окна; у Resilience4j по умолчанию 100). Имя метрики в спеке
  было `resilience_…` — у библиотеки `resilience4j_circuitbreaker_state`, спека и алерт по ней. Отказов
  подменного API в интеграционных тестах четыре на весь прогон — окно из десяти они не открывают.
  Старый код тестов не проходил бы: предохранителя и его метрик не было.
