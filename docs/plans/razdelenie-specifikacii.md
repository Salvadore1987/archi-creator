# Разделение спецификации Archi Creator на части

## Контекст

`docs/archi-creator.md` — 1266 строк, 13 разделов: от обзора продукта до формата Git-выгрузки.
Документ живой (правится по ходу работы), но в одном файле у него три разных читателя:
бэкендер (кодек, API, ИИ, Git), фронтендер (визуальный язык, дерево, канва) и тот, кто
заводит схему и миграции. Любая правка одной части создаёт конфликт с правками двух других,
а найти нужный раздел в полуторатысячной простыне тяжело.

Задача: разложить содержимое по трём файлам — backend, frontend, database — оставив
`archi-creator.md` связующим документом: обзор, требования, общая архитектура, этапы,
открытые вопросы и карта разделов.

**Ограничение:** текст переносится без изменений. Правятся только заголовки файлов
и перекрёстные ссылки. Замечания по схеме БД (та самая валидация, с которой начался разговор) —
отдельным шагом после разделения, чтобы diff переезда не смешивался с diff правок по существу.

## Ключевое решение: нумерация разделов сохраняется

В документе ~80 ссылок вида `§4.4`, `§11.2`, `§6.10` и 103 упоминания `FR-xx`/`NFR-xx`.
Если перенумеровать разделы в каждом файле с единицы, придётся переписать все ссылки
и после этого никто не найдёт «§11.4», на которую ссылаются рабочие обсуждения.

Поэтому **исходные номера остаются в частях**: `spec/backend.md` начинается с «## 3.3»,
`spec/database.md` — с «## 4», `spec/frontend.md` — с «## 6. Визуальный язык».
Нумерация сквозная по всему комплекту, файл — лишь контейнер. Ссылка `§4.4` остаётся
валидной строкой; внутри файла она становится якорем, между файлами — ссылкой на файл.

### Пограничные случаи — решения

- **§6.10 (экспорт SVG/PNG)** уезжает в backend: это серверный писатель. Во `frontend.md`
  на его месте остаётся не копия, а два обязательства фронта из того же раздела —
  узлы рисуются инлайн-SVG, а не CSS, геометрия читается из общего `shapes.json` (FR-42), —
  и ссылка на §6.10.
- **§11.6** физически лежит в `database.md` (это чек-лист полей схемы: разреженный
  `sort_order`, `git_sha`, `git_*` у `Workspace`, реально заполняемый `raw_xml`).
  В `backend.md` §11 заканчивается ссылкой на него.
- **§9.3** остаётся целиком в backend. В `database.md` добавляется короткий абзац
  «Чем проверяется хранение» — ссылками на §9.1 (`git_roundtrip`) и §9.3 (импорт → БД →
  экспорт, конкурентное сохранение, версии), без копирования текста.
- **§7 ИИ** — в backend. Сущность `AiAuditLog` остаётся в §4.1 (`database.md`),
  §7.5 ссылается на неё.

## Структура файлов

### archi-creator.md (главный)

1. Заголовок и статус — как есть.
2. **Новый раздел «Состав спецификации»** сразу после §1: таблица «файл → что внутри →
   какие разделы» плюс правило, что нумерация сквозная, а FR/NFR живут здесь.
3. §2, §3.1, §3.2 — без изменений.
4. Для каждого уехавшего раздела **остаётся заголовок с исходным номером и одна строка-указатель**:

   ```markdown
   ## 4. Модель данных

   → [`spec/database.md`](spec/database.md) — сущности, индексы и ограничения,
   стратегия хранения, ретеншен версий (§4.1–§4.4).
   ```

   Это сохраняет оглавление главного файла целиком: по нему видно устройство продукта,
   а §-ссылка из любого обсуждения резолвится в один клик.
5. §10, §12, §13 — без изменений. В §12 к каждому этапу добавляется ссылка на файл,
   где описано содержание этапа.

### spec/backend.md, spec/frontend.md, spec/database.md

Единая шапка у каждого:

```markdown
# Archi Creator — <бэкенд | фронтенд | хранение данных>

> Часть спецификации [`archi-creator.md`](../archi-creator.md). Нумерация разделов
> сквозная по всему комплекту, требования `FR-xx`/`NFR-xx` — в §2 главного файла.
> Документ живой: решения правятся здесь, а не в переписке.

**Содержание:** §3.3 · §3.4 · …
```

Далее — перенесённые разделы в исходном порядке, дословно.

## Перекрёстные ссылки

Правило: ссылка внутри своего файла остаётся голой (`§6.6`), ссылка в чужой файл
становится markdown-ссылкой на файл и якорь.

| Откуда | Куда | Как выглядит после правки |
|--------|------|---------------------------|
| backend.md §4.4-упоминания | database.md | `[§4.4](database.md#44-хранение-и-очистка-версий)` |
| frontend.md → §6.10, §9.1 | backend.md | `[§6.10](backend.md#610-экспорт-представлений)` |
| database.md → §11.2, §3.4 | backend.md | `[§11.2](backend.md#112-формат-разложенный-yaml)` |
| части → §2, §3.1, §10.3, §12 | ../archi-creator.md | `[§10.3](../archi-creator.md#103-профили-и-конфигурация)` |
| главный → уехавшие разделы | spec/*.md | `[spec/backend.md](spec/backend.md)` |

Якоря — GitHub/GitLab-стиль: заголовок в нижний регистр, точки и прочая пунктуация
убираются, пробелы → дефисы, кириллица сохраняется (`### 4.4 Хранение и очистка версий`
→ `#44-хранение-и-очистка-версий`).

Отдельно: единственная внешняя ссылка документа — макеты в §6.5 —
`(mockups/index.html)` превращается в `(../mockups/index.html)`, потому что §6.5
уезжает на уровень вниз, в `spec/frontend.md`.

## Порядок работ

1. Создать `docs/spec/`.
2. Нарезать три файла механически по диапазонам строк из таблицы выше
   (`sed -n 'A,Bp'`), добавить шапки и строку «Содержание».
3. Переписать `docs/archi-creator.md`: раздел «Состав спецификации», замена уехавших
   разделов на указатели, ссылки в §12.
4. Пройти перекрёстные ссылки по таблице выше во всех четырёх файлах.
5. Добавить во `frontend.md` заметку о `shapes.json`/инлайн-SVG и в `database.md`
   абзац «Чем проверяется хранение» — оба только ссылками, без копий текста.
6. Скопировать этот план в `docs/plans/razdelenie-specifikacii.md` (правило из CLAUDE.md:
   план живёт в репозитории) и отметить в нём принятые решения по границам разделов.

## Проверка

- **Ничего не потеряно.** `cat` трёх частей и главного без новых шапок и указателей
  даёт тот же набор непустых строк, что и исходник: сверка через
  `diff <(отсортированные непустые строки исходника) <(то же по четырём файлам)` —
  расхождения только на добавленных шапках, указателях и заголовке «Состав спецификации».
  До правок сохранить копию исходника в scratchpad для сверки.
- **Все §-ссылки резолвятся.** Собрать список `grep -o '§[0-9.]*'` по четырём файлам
  и сверить с фактическими заголовками: каждый упомянутый раздел существует ровно в одном файле.
- **Все `FR-xx`/`NFR-xx` из частей есть в §2 главного** — тем же способом: сравнить
  множество упоминаний с множеством строк таблиц требований. Должно найтись 53 FR и 8 NFR.
- **Ссылки на файлы рабочие.** Проверить, что каждый относительный путь
  (`../archi-creator.md`, `spec/database.md`, `../mockups/index.html`) указывает
  на существующий файл.
- **Глазами:** открыть `docs/archi-creator.md` и убедиться, что оглавление §1…§13
  читается целиком и по каждому уехавшему разделу видно, где он теперь.

### Решения, принятые по ходу (не было в исходном плане)

- **`### Состав спецификации` — подраздел §1**, а не отдельный нумерованный раздел:
  иначе пришлось бы сдвигать нумерацию §2…§13 и ломать все внешние ссылки.
- **Ссылки внутри указателей главного файла не превращались в markdown-ссылки.**
  В стабах вида «→ `spec/database.md` — сущности (§4.1), индексы (§4.2)…» ссылка на файл
  уже стоит в том же предложении; дублировать её на каждом номере — шум. Автоматическая
  простановка ссылок прошла по §2, §10, §12, §13, то есть по разделам, которые
  главный файл держит у себя.
- **Заголовок `## 9. План тестирования` продублирован** в `backend.md` и `frontend.md`:
  §9.1–9.3 и §9.4 живут в разных файлах, и без общего заголовка §9.4 повисает.
  В каждом файле рядом стоит ссылка на вторую половину.
- **`database.md` получил новый раздел «Чем проверяется хранение»** — таблица ссылок
  на §9.1 и §9.3. Своих тестов у схемы нет, но без этой таблицы из файла не видно,
  чем она вообще покрыта.
