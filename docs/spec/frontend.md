## 6. Визуальный язык

### 6.1 Принцип

Силуэт и иконка — от ArchiMate, оформление — новое. Проверка: архитектор, знающий Archi,
опознаёт тип фигуры без подписи типа.

Сохраняется: форма контура (прямоугольник, скруглённый прямоугольник, овал, фигура
с «ушком» и т. д.), позиция угловой иконки (правый верхний угол), цветовое кодирование
слоя, направление и оформление стрелок связей согласно нотации.

Меняется: радиус скругления, толщина и цвет обводки, заливка, тень, шрифт и иерархия
подписей, качество иконок, отступы.

### 6.2 Токены

**Тема одна: графитовый корпус, светлый холст.** Решение принято 22.09.2026, переключателя
тем не будет. Причина не в экономии: цвета слоёв ArchiMate пастельные и рассчитаны
на светлый фон — на тёмном они превращаются в грязь и требуют второй, несовместимой
палитры. Светлый холст к тому же совпадает с тем, что уйдёт в экспорт ([§6.10](backend.md#610-экспорт-представлений)) и в документы,
а тёмный корпус вокруг него снимает основную нагрузку на глаза. Тёмная тема панелей
при светлом холсте — это и есть текущий выбор.

### 6.3 Правила отрисовки узла

```
╭────────────────────────╮   контур = силуэт типа ArchiMate
│ ▣  Payment Gateway     │   иконка 14×14 слева или в правом верхнем углу
│    Application Component│   подпись типа — опциональна (настройка вида)
╰────────────────────────╯   заливка = токен слоя, обводка = border-токен
```

- Имя — в одну-две строки с переносом, обрезка многоточием на третьей.
- Приоритет стиля: собственный `fillColor`/`font` объекта → токен слоя.
- Выделение — двойная обводка акцентным цветом, не изменение заливки (чтобы не терять слой).
- Наведение — усиление тени и показ точек подключения связей.

### 6.4 Связи

Стиль наконечников и линий соответствует нотации ArchiMate (ромб composition,
пустой ромб aggregation, треугольник realization, пунктир и т. д.) — это часть
семантики, а не оформления, и не меняется. Улучшается: ортогональная маршрутизация,
скругление углов, поведение при наведении, читаемость подписи связи.

### 6.5 Компоновка главного экрана — решение принято

**Выбран вариант A «Панели»** (22.09.2026). Четырёхпанельный макет: слева дерево модели
и палитра, в центре вкладки представлений и холст, справа свойства и панель помощника,
снизу статус-строка. Причина выбора — пересадка с Archi без переучивания и то, что
дерево, палитра, свойства и находки видны одновременно.

Отклонены и сохранены как снимки альтернатив:
**B «Холст»** (канва во весь экран, плавающие панели) — дерево модели не на виду, что
критично для 242 приложений; **C «Два режима»** (отдельный режим просмотра для `VIEWER`) —
два интерфейса вместо одного. Идея режима просмотра из C не выброшена: содержательная
часть (описание элемента, участие в связях, анализ влияния) перенесена в правую панель
варианта A отдельной вкладкой рядом со «Свойствами» — §6.7.

**Макеты: [`docs/mockups/index.html`](../mockups/index.html)** (`open docs/mockups/index.html`).
Там же галерея фигур с переключателем «новый стиль / классический Archi» и нотация связей.

### 6.6 Дерево модели (левая панель)

Дерево — основной инструмент навигации: в вашей модели 402 элемента, 368 связей и
12 представлений, и на такой объём «просто список папок» не работает.
Макет собран на реальных данных из `Hamkorbank_AS_IS_strict.archimate`
(`docs/mockups/tree-data.js` генерируется из файла), поэтому проверен на настоящих объёмах.

**Структура.** Папки берутся из файла как есть, включая пользовательскую вложенность:

```
STRATEGY                 69     BUSINESS                47
  Capability map                   Акторы
    Клиентские сервисы             Бизнес-линии
    Управление маркетингом…        Процессы CRM Creatio
APPLICATION             242     TECHNOLOGY & PHYSICAL   42
  Внешние системы        50        Сети
    Центральный банк               ЦОД → ЦОД Ташкент / ЦОД Андижан
    Государственные ИС             Системное ПО
    Процессинги…                 OTHER                    2
  Каналы                 17     RELATIONS              368
  Фронты сотрудников     21     VIEWS                   12
  Цифровой офис           7
  Интеграционный слой    12
  Мастер-системы         72
  Микросервисы           63
```

**Состав панели сверху вниз:**

| Блок | Поведение |
|------|-----------|
| Поиск | Живой фильтр по имени и типу, ⌘F/Ctrl+F, Esc сбрасывает. Совпадение подсвечивается, ветви с совпадениями разворачиваются автоматически, остальные скрываются. Счётчики в папках пересчитываются под запрос. |
| Режим группировки | **Папки** — структура файла. **Типы** — все элементы по типу, группы отсортированы по количеству (Application Component 242, Capability 69, Business Process 40, …). **Список** — плоский алфавитный перечень. |
| Фильтры | «Все», «На представлении» (элементы открытой диаграммы), «Не размещены» (`v = 0`), «Замечания» (элементы из отчёта валидации). Фильтр комбинируется с поиском. |
| Дерево | Направляющие уровней, счётчик по ветви (рекурсивный), в папке `Relations` — число связей. |
| Подвал | Общая статистика модели; при активном фильтре — «показано N». |

**Маркеры на строке элемента** (правый край):

- `○` — не размещён ни на одном представлении (45 таких в вашей модели);
- `●` красный — по элементу есть находка помощника;
- `×N` — размещён в N представлениях (полезно для оценки связности; у `IABS` — 4).

**Взаимодействие.**

- Выбор элемента в дереве → выделение на холсте (если он есть на открытом представлении),
  заполнение панели свойств, переключение палитры на слой этого элемента, отражение в статус-строке.
- Обратно: выбор объекта на холсте → подсветка и прокрутка к строке в дереве.
- Перетаскивание элемента из дерева на холст размещает его на текущем представлении (FR-12).
- Находки помощника управляют деревом: «Показать в дереве» у дубликатов включает поиск
  `IABS`, у сирот — фильтр «Не размещены».

**Производительность.** В одной ветви рендерится не более 50 строк, дальше — «ещё N — показать»;
в плоском списке — 120. Это держит DOM в сотнях узлов вместо тысяч при 2 000 элементов (NFR-01).

### 6.7 Вкладка «Описание» (правая панель)

Правая панель имеет две вкладки: **«Свойства»** — форма редактирования (имя, тип, папка,
свойства key/value, идентификатор) — и **«Описание»** — карточка элемента для чтения,
перенесённая из отклонённого варианта C. Вторая закрывает сценарий «разобраться, что это
за система и что сломается при её отказе», для которого форма редактирования не годится.

Состав карточки:

| Блок | Содержимое |
|------|-----------|
| Заголовок | Имя, тип, слой, признак «есть замечание», число представлений |
| Документация | Поле `documentation` из модели. Если пусто — тип и путь в дереве, без выдуманного текста |
| Участвует в связях | Все связи элемента: направление (→ исходящая, ← входящая), тип в русской формулировке («обслуживает», «состоит из», «реализует»), второй конец с иконкой своего типа. Первые 7, далее «показать все N». Клик по строке переводит выбор на этот элемент |
| Анализ влияния | Считается по исходящим связям типов Serving, Realization, Triggering, Flow, Access: кто ломается напрямую, сколько элементов задето вторым уровнем, сколько вложенных элементов включает. Для элемента без связей — прямое указание, что он ни с чем не связан |
| Свойства | `property key/value` из модели |
| Размещён в представлениях | Список представлений; текущее подсвечено |
| Собрать документацию | Запуск FR-26. Результат — текст, модель не меняется |

Пример на реальных данных (`IABS`): 60 связей, «при отказе напрямую затрагиваются 12 —
«Карты», «UzASBO», «QR-Online» и ещё 9; через них — ещё 12 элементов второго уровня;
включает 44 вложенных элемента». Свойства `source = Hamkorbank ALL.vsdx, страницы as is`,
`owner = FIDO`, `db = Oracle 19c` — прямо из файла.

**Навигация.** Клик по связи в карточке выбирает второй элемент: раскрывает ветви дерева
до него, прокручивает к строке, перерисовывает карточку и обновляет холст. Это основной
способ «ходить» по модели там, где элемента нет на открытом представлении.

**Поведение по ролям (FR-33).** Вкладка по умолчанию зависит от роли:

| | `VIEWER` | `ARCHITECT` / `ADMIN` |
|---|---|---|
| Правая панель открывается на | **«Описание»** | «Свойства» |
| Вкладка «Свойства» | доступна, поля только для чтения | редактируемая форма |
| Панель инструментов канвы | скрыта | видна |
| Палитра элементов | скрыта, место отдано дереву | видна |
| Статус модели в шапке | «только чтение» | «Редактирует: <имя>» |
| Экспорт `.archimate`, поиск, помощник | доступны | доступны |

Логика простая: форма редактирования читателю бесполезна, а карточка с документацией,
связями и анализом влияния — именно то, зачем он открыл модель. Скрытие палитры
не косметика: она освобождает примерно 200 px высоты, и дерево показывает почти вдвое
больше строк без прокрутки.

В макете роль переключается тумблером `ARCHITECT / VIEWER` в правом верхнем углу —
это элемент макета, в продукте роль приходит из Keycloak (FR-28).

### 6.8 Редактирование дерева

Дерево — не только навигация, но и основной способ приводить модель в порядок после
импорта из Visio: переименовать, разложить по папкам, вычистить сирот. Всё перечисленное
реализовано в макете и работает на настоящих 402 элементах.

**Операции**

| Действие | Как вызывается | Поведение |
|----------|----------------|-----------|
| Переименование | `F2` или двойной клик по имени | Поле правки прямо в строке. `Enter` — применить, `Esc` — отменить, потеря фокуса — применить. Имя меняется и в панели свойств, и на холсте, если элемент размещён на открытом представлении |
| Перемещение | Перетаскивание на строку папки; «Переместить в папку…» в контекстном меню | Перетаскивание работает и для множественного выделения; папка-приёмник подсвечивается. Диалог выбора ищет по полному пути («Application / Интеграционный слой»), что на 30+ папках быстрее, чем раскрывать дерево |
| Создание папки | Кнопка `+` в шапке панели; «Создать вложенную папку» в меню папки | Папка создаётся внутри папки выбранного элемента и сразу переходит в режим переименования |
| Удаление | `Delete`/`Backspace`; пункт меню; кнопка в панели группового выделения | Перед удалением показывается число затрагиваемых связей и сколько элементов размещено на открытом представлении. Удаление уносит связи вместе с элементами |
| Множественное выделение | `Ctrl`/`Cmd` + клик — переключение; `Shift` + клик — диапазон по видимым строкам; «Выделить все элементы» в меню папки | Правая панель переключается на сводку: сколько выбрано, сколько задето слоёв и папок, список, групповые «Переместить» и «Удалить» |
| Отмена и повтор | `⌘Z` / `⇧⌘Z`, кнопки на панели инструментов, «Отменить» в сообщении о действии, панель истории | Многошаговые, на всю сессию (§6.9) |

**Несохранённые изменения.** Изменённые элементы помечаются точкой в дереве, статус-строка
показывает счётчик, кнопка «Сохранить» появляется только когда есть что сохранять.
Это прямое следствие модели блокировок (FR-05): пока модель у вас, правки живут локально
до явного сохранения, создающего версию (FR-06). Подробности учёта — §6.9.

**Ограничения, заложенные сознательно**

- Системные папки формата удалению не подлежат — сообщение объясняет почему.
- Перетаскивание меняет папку, но не порядок внутри папки: порядок узлов значим для
  round-trip ([§3.4](backend.md#34-кодек-archimate--ключевые-решения), п. 3), и менять его случайным перетаскиванием опаснее, чем полезно.
  Если понадобится — делать отдельной явной операцией.
- Связи в дереве не редактируются: они живут в папке `Relations` и правятся на холсте.

### 6.9 История изменений

Отмена — многошаговая на всю сессию, а не на одно действие: правки после импорта из Visio
идут пакетами (переименовал десяток, разложил по папкам, вычистил сирот), и одношаговая
отмена в таком режиме бесполезна.

**Модель.** Каждая операция кладётся в стек парой функций `apply` / `revert` и списком
затронутых элементов. Отмена вызывает `revert` и сдвигает указатель назад, повтор —
`apply` вперёд. Новая операция после отмены обрезает ветвь «вперёд» — обычное поведение
линейной истории.

```
стек:  [0] Переименование «IABS» → «IABS — ядро учёта»   ← сохранено
       [1] Перемещено 1 → «Цифровой офис»
       [2] Удалено 1                                     ← сейчас
указатель: 2   точка сохранения: 0   → несохранённых изменений: 2
```

**Вызов:** `Ctrl/Cmd+Z` — отменить, `Ctrl/Cmd+Shift+Z` и `Ctrl+Y` — повторить; кнопки
на панели инструментов (неактивны, когда отменять или повторять нечего, подсказка
показывает название конкретной операции); «Отменить» / «Вернуть» в сообщении о действии;
панель истории по клику на счётчик изменений в статус-строке — список операций с текущей
позицией и точкой сохранения, клик по строке возвращает модель в это состояние.

**Пометка «изменён».** Считается не операцией, а разницей между текущей позицией
и точкой сохранения: отмена снимает пометки сама, а не оставляет их висеть.
Отмена *за* точку сохранения тоже считается несохранённым изменением — модель в этот
момент отличается от сохранённой версии.

**Границы.** История живёт в сессии редактирования и обнуляется при закрытии модели;
сохранение не очищает её, а лишь двигает точку сохранения — можно сохранить, потом
отменить и увидеть, что расхождение с версией вернулось. Совместно редактируемой истории
нет и не нужно: модель под блокировкой у одного архитектора (FR-05).

**Дефект, найденный при сборке макета** (регрессия вероятна, из кода причина не видна):
выделение строки прокручивало её в зону видимости на каждый клик, из-за чего строка
уезжала из-под курсора и двойной клик по имени не срабатывал. Исправлено: клик внутри
дерева не прокручивает — строка и так перед глазами; прокрутка остаётся только когда
выделение приходит извне (с холста, из связи в карточке, из находки помощника).

Печать представления в SVG и PNG — серверная, описана в
[`backend.md` §6.10](backend.md#610-экспорт-представлений). Браузер пользователя в ней
не участвует, но два обязательства ложатся на канву и действуют начиная с этапа 3:

1. **Фигура узла рисуется инлайн-SVG внутри узла React Flow, а не средствами CSS.**
   Пока типы фигур не написаны, решение бесплатное; после — переписывание всех типов.
2. **Геометрия контуров, позиции иконок, радиусы и отступы берутся из общего `shapes.json`**,
   иконки — из общего спрайта. Канва и серверный писатель читают одно и то же (FR-42),
   иначе экран и файл разойдутся.

Расхождение ловится визуальными тестами §9.4.

### 9.4 E2E (Playwright)

Сценарии:
- Импорт файла → открытие представления → все объекты отрисованы.
- Drag-and-drop из палитры → элемент появился в дереве модели и на канве.
- Рисование недопустимой связи → тип не предлагается.
- Вложенность: перенос элемента внутрь другого → создана подразумеваемая связь.
- Авторазметка: слои выстроены сверху вниз.
- Undo/redo цепочки из пяти операций.
- Экспорт → скачанный файл открывается импортом обратно.
- Панель ИИ: ревью выдаёт находки, переход к элементу выделяет его на канве.

**Визуальные снимки**: по одному снимку на каждый тип элемента при 100 % зума, плюс
снимки типовых представлений. Изменения визуального языка сверяются с эталонами осознанно.

**Сверка канвы и экспорта (FR-42)**: для того же набора фикстур снимок канвы сравнивается
с PNG, полученным серверным экспортом. Это единственное, что не даёт двум рендерерам
разойтись; расхождение выше допуска — падение сборки.
