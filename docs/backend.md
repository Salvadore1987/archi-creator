### 3.3 Состав модулей бэкенда

| Пакет | Ответственность |
|-------|-----------------|
| `web` | REST-контроллеры, DTO, обработка ошибок (`@RestControllerAdvice`) |
| `service` | Бизнес-логика: модели, импорт/экспорт, валидация, блокировки, версии, ИИ |
| `repository` | Spring Data JPA репозитории |
| `entity` | JPA-сущности ([§4](database.md#4-модель-данных)) |
| `archi` | Кодек `.archimate`: `ArchiReader`, `ArchiWriter`, `ArchiTypeRegistry` (маппинг `xsi:type` ↔ внутренний тип), `RawXmlFragment` для неподдержанных узлов |
| `oef` | Экспорт в Open Exchange Format (§3.5): `OefWriter`, проверка результата по XSD, отчёт о потерях |

| `ai` | Построение контекста модели для Claude, парсинг структурированных ответов, аудит |
| `security` | Конфигурация Spring Security, маппинг ролей Keycloak, проверка ACL |

### 3.4 Кодек `.archimate` — ключевые решения

Формат Archi устроен так (подтверждено на `Hamkorbank_AS_IS_strict.archimate`):

```xml
<archimate:model name="…" id="id-9c7b…" version="5.0.0">
  <folder name="Strategy" id="id-2655…" type="strategy">
    <folder name="Capability map" id="id-09c1…">     <!-- вложенные папки без type -->
      <element xsi:type="archimate:Capability" name="…" id="id-d55d…">
        <property key="source" value="…"/>
      </element>
  <folder type="relations"> … связи …
  <folder type="diagrams">
    <element xsi:type="archimate:ArchimateDiagramModel" name="01 Контекст AS IS" id="…">
      <documentation>…</documentation>
      <child xsi:type="archimate:DiagramObject" id="…" archimateElement="id-ccd4…"
             targetConnections="id-5fca… id-e581…">
        <bounds x="20" y="60" width="150" height="60"/>
        <sourceConnection xsi:type="archimate:Connection" id="…" source="…" target="…"
                          archimateRelationship="id-3399…"/>
      </child>
      <child xsi:type="archimate:Group" name="Каналы">   <!-- группы содержат вложенных детей -->
```

Из этого следуют требования к кодеку:

1. **Идентификаторы сохраняются буквально.** Формат — любой допустимый для Archi; при импорте id не
   перегенерируются. Новые объекты получают `id-<32 hex>`, как в самом Archi
   ([`ADR-0002`](../spec/adr/0002-dual-identity.md)).
2. **Папки — часть модели, а не производная величина.** Девять корневых папок
   (`strategy`, `business`, `application`, `technology`, `motivation`,
   `implementation_migration`, `other`, `relations`, `diagrams`) плюс произвольная вложенность пользовательских папок.
   Дерево папок хранится в БД и восстанавливается при экспорте.
3. **Порядок узлов сохраняется.** У каждой сущности есть `sort_order` в пределах родителя;
   писатель обходит дерево в том же порядке, что и читатель. Это условие round-trip.
4. **Координаты `bounds` относительны родителю** (у детей внутри `Group` — относительно
   группы). Внутреннее представление хранит их так же, чтобы не терять точность.
5. **Неизвестные узлы и атрибуты складываются в `RawXmlFragment`** (сырой XML-текст,
   привязанный к родителю и позиции) и выводятся без изменений.
6. **`targetConnections` — производная величина**: восстанавливается из множества
   `sourceConnection`, но порядок идентификаторов в атрибуте сохраняется как есть.

### 3.5 Экспорт в Open Exchange Format

Односторонняя выгрузка для инструментов кроме Archi (BiZZdesign, Sparx и прочих),
для регулятора и для подрядчиков. Пространство имён
`http://www.opengroup.org/xsd/archimate/3.0/`, результат проверяется по официальной XSD
перед отдачей.

**Импорта из OEF нет.** Единственный принимаемый формат — `.archimate` (FR-01).
Решение сознательное: приём второго диалекта требует разбора чужих вольностей
и собственного набора golden-file тестов, а сценария «нам присылают модели не в Archi»
нет. Появится — заводится отдельной задачей, писатель к тому моменту уже даст
проверенную таблицу соответствия.

**OEF — формат обмена, а не хранения.** Обещание lossless round-trip (NFR-05) относится
только к `.archimate`. Часть данных через OEF пройти не может физически, поэтому каждая
выгрузка даёт отчёт о потерях.

**Что во что превращается при выгрузке**

| Наша модель | OEF | Замечание |
|-------------|-----|-----------|
| Папки (`folder`) | `organizations` → `item` | Дерево сохраняется, элемент — `item identifierRef`; тип корневой папки (`application`, `relations`…) в OEF не выражается — принимающий инструмент разложит по своим правилам. Свойства папок не переносятся: у `item` их нет |
| Элементы, связи | `elements`, `relationships` с типом OEF | Тип без префикса и без `Relationship`; `Junction` — `AndJunction`/`OrJunction`; `accessType` Archi — `Write`/`Read`/`Access`/`ReadWrite` (отсутствие атрибута в Archi — запись, в OEF — `Access`, поэтому пишется явно); `directed` — `isDirected`; `strength` — `modifier` |
| Типы, неподдержанные в редакторе (`Location`, `Grouping`, фаза 3) | свои типы OEF | **Переносятся**: opaque — свойство редактора, а не формата. OEF знает все типы ArchiMate 3.1 |
| `property key/value` на объекте | `propertyDefinitions` + ссылки `propertyDefinitionRef` | Ключи выносятся в общий словарь модели (`propid-N` в порядке первого появления), значения остаются у объектов |
| `name`, `documentation`, `purpose` модели | `name`/`documentation` с `xml:lang="ru"` | OEF многоязычен, мы пишем один язык. Имя элемента в OEF обязательно — пустое пишется пустым |
| Геометрия представлений | `view` → `node`, `connection` | Координаты в OEF абсолютные (у нас — относительно родителя), размер `-1` подставляется по типу из `shapes.json`. Вложенность — вложенные `node` (`Container` у группы, `Element` у элемента). Точки перегиба — из смещений от центров в абсолютные той же формулой, что у канвы: картинка та же. Отрицательных координат OEF не допускает — представление сдвигается целиком, сдвиг — в отчёте |
| Группа, заметка, ссылка на представление | `Container`, `Label`, `Label` + `viewRef` | Подпись группы и текст заметки — `label` |
| Стиль объекта (`fillColor`, `lineColor`, `alpha`, `font`, `fontColor`, `lineWidth`) | `style` | Цвета — `r g b` и прозрачность `a` в процентах; шрифт — имя, размер с шагом 0,5 и начертание. Остальное оформление (`textAlignment`, `textPosition`, `gradient`, тип фигуры…) не выражается — в отчёте |
| `raw_xml` неподдержанных сущностей (FR-03) | — | **Не переносится.** То, что сохранено как непрозрачное из чужого `.archimate`, в OEF выразить нечем; каждый фрагмент — запись отчёта. То же — представления не-ArchiMate (`SketchModel`, `canvas:*`) и объекты на них |
| Идентификаторы | `identifier` | Формат `id-<hex>` валиден как XML NCName, идентификаторы сохраняются; не годный для `xs:ID` (старые модели) заменяется на `id-<hex>` от него самого — в отчёте |

**Отчёт о потерях** отдаётся вместе с файлом: список объектов, у которых что-то
не перенеслось, с причиной. Без него формат превращается в тихую потерю данных — ровно
то, против чего затевался строгий round-trip `.archimate`. Полнота держится
построением, а не перечнем известных случаев: у каждого вида объекта закрытый список
переносимых атрибутов и значений, всё прочее попадает в отчёт.

**Как отдаётся.** `GET /models/{id}/export?fmt=oef` — zip из `<слаг модели>-v<N>.xml`
и `loss-report.json`, число записей — в `X-Archi-Loss-Count`; архив детерминирован.
Источник — снимок зафиксированной версии (`INV-IXC-008`), как у CSV и картинок.
Результат проверяется по официальной XSD 3.1 (`archimate3_Diagram.xsd`, она включает
`View` и `Model`); схемы лежат в ресурсах сборки, в сеть за ними сервер не ходит.
Не прошёл — `500 IXC_OEF_SCHEMA_VIOLATION`, файл не отдаётся (FR-43).
Сценарий — [`UC-IXC-005`](../spec/application/interchange/usecases/export-open-exchange.md).

### 5.2 Экспорт каталога в CSV

Назначение — отдать ландшафт людям, которые не будут открывать редактор: владельцам
систем на согласование, аудиту, руководству. **Обратной загрузки нет**: таблица
не является источником правды, и приём правок из Excel вернул бы задачу слияния,
которую §11.4 решает в одном месте — через Git.

`GET /models/{id}/export?fmt=csv` отдаёт zip с двумя файлами:

```
elements.csv
  id;type;name;layer;folder;documentation;views;placed;<свойства…>
  id-2ae470c0…;Application Component;IABS;Application;Application / Мастер-системы;;4;да;…

relations.csv
  id;type;source_id;source_name;target_id;target_name
  id-3399b633…;Serving;id-2ae470c0…;IABS;id-d8979413…;Интернет банкинг ФЛ
```

**Решения по формату файла** (иначе он не откроется у получателя):

- **UTF-8 с BOM** — без BOM русский Excel читает файл как windows-1251 и показывает кракозябры.
- **Разделитель `;`** — в русской локали Excel `,` не считается разделителем полей,
  и весь ряд попадает в одну ячейку. Параметр `sep=,` для тех, кому нужен стандартный CSV.
- **Столбцы свойств генерируются динамически** из ключей, встречающихся в модели:
  `source`, `owner`, `criticality`, `db` — это и есть самое ценное в каталоге приложений.
  Порядок столбцов — по частоте ключа, чтобы заполненные шли первыми.
- Имена вместе с идентификаторами в `relations.csv`: без имён таблица нечитаема,
  без идентификаторов её нельзя сверить с моделью.

Параметр `folder=<id>` ограничивает выгрузку поддеревом — «каталог приложений»
обычно означает `Application`, а не всю модель.

### 6.10 Экспорт представлений

Форматы: **SVG и PNG, экспорт серверный.** PDF в объём не входит — пользователю доступна
печать из браузера, а вкладывать в документы и презентации нужны именно картинка и вектор.

**Механизм.** Сервер берёт представление из снимка зафиксированной версии и печатает SVG:
контуры фигур, иконки, связи с наконечниками, подписи. Источник — снимок, а не текущие
таблицы: выгрузка прибита к версии (INV-IXC-008), и пакет всех представлений не смешивает
состояния. Браузер пользователя в этом не участвует, поэтому экспорт работает и по API,
и пакетом, и из генератора документации (FR-26). PNG получается растеризацией того же
SVG — отдельного пути отрисовки для растра нет.

```
снимок версии (.archimate) ──▶ SvgWriter (Java) ──▶ .svg  (текст, шрифт вшит подмножеством)
                                          └───▶ .svg в кривых ──▶ Batik ──▶ .png @1x/@2x/@4x
```

Растр строится из варианта с подписями в кривых: Batik тогда не зависит от шрифтов
системы образа, а текст в PNG — те же контуры глифов, что в SVG `outline=true`.
Печатается только SVG 1.1 без CSS: наконечники связей и ореол подписи — явной геометрией,
а не `marker` с `auto-start-reverse` и `paint-order`, — их не понимают ни Batik,
ни Inkscape, ни Word.

**Один визуальный язык на два рендерера.** Канва рисует узлы в браузере, сервер — в файл;
это две реализации, и они разойдутся, если ничего не предпринять. Поэтому:

1. Фигура узла на канве рисуется **инлайн-SVG внутри узла React Flow**, а не средствами
   CSS. Это решение этапа 3: пока типы фигур не написаны, оно бесплатное, после —
   переписывание всех типов.
2. Геометрия контуров, позиции иконок, радиусы и отступы выносятся в общий
   `shapes.json`, иконки — в общий спрайт. Оба рендерера читают одно и то же (FR-42).
3. Расхождение ловится тестом: визуальный снимок канвы и экспортированный SVG
   сравниваются на наборе фикстур ([§9.4](frontend.md#94-e2e-playwright)). Без этого теста правило из п. 2 держаться не будет.

Остаётся честная зона расхождения — **перенос строк в подписи**: браузер переносит текст
сам, сервер обязан считать сам. Сервер использует тот же шрифт, что канва, — Inter из токенов
(`spec/ui/design-tokens.yaml`), статические начертания одного выпуска в `ui/fonts/` classpath:
канва подключает WOFF2, сервер читает TTF. Перенос жадный по словам с кернингом, слово шире
строки рвётся по символам; допуск проверяется теми же визуальными тестами.
*(До 2026-10-12 здесь стояли Archivo и IBM Plex Mono — расхождение с токенами; нормативны
токены.)*

**Параметры экспорта**

| Параметр | Значения | Назначение |
|----------|----------|-----------|
| `fmt` | `svg`, `png` | Формат |
| `scale` | `1`, `2`, `4` | Плотность PNG |
| `outline` | `false` (по умолчанию), `true` | В SVG текст остаётся текстом (шрифт вшит в файл, есть fallback-стек) — так он ищется и копируется. `outline=true` переводит подписи в кривые для получателей без наших шрифтов: Inkscape, Word, внешние подрядчики |
| `background` | `paper` (по умолчанию), `transparent` | Фон под диаграммой |

**Ограничения.** Экспортируется представление целиком по границам содержимого, с полями
в шаг сетки. Верхняя граница — 4 000 × 4 000 логических единиц при `scale=4`, то есть
16 000 px по стороне PNG; выше запрос отклоняется (`IXC_IMAGE_TOO_LARGE`) с наибольшей
допустимой плотностью. У SVG предела нет. Пакетный экспорт модели отдаёт zip с файлом
на представление, имена — слаги представлений (та же функция, что в §11.2:
`<слаг>.<8 hex>.<ext>`), и `loss-report.json`.

**Отчёт о потерях** (INV-IXC-006) у картинки перечисляет то, что она передаёт не так,
как модель: объект неподдержанного типа нарисован заглушкой, шрифт объекта заменён
на Inter, подпись усечена, изображение узла не нарисовано. Одиночная выгрузка отдаёт
число записей в заголовке `X-Archi-Loss-Count`, пакет — весь отчёт в архиве.
Сценарий — [`UC-IXC-004`](../spec/application/interchange/usecases/export-view-image.md).

**Инструмент растеризации** — Apache Batik: остаётся в JVM, не тянет в образ нативных
зависимостей. Если упрёмся в качество текста, замена — `resvg` отдельным бинарником;
интерфейс `Rasterizer` для этого предусмотрен сразу.

## 7. ИИ-помощник

### 7.1 Границы

Помощник **только советует**. Он не создаёт, не изменяет и не удаляет объекты модели.
Все его ответы — текст, ссылки на существующие элементы и структурированные предложения,
которые архитектор реализует вручную. Это решение принято сознательно: модель — рабочий
артефакт банка, и её изменения должны быть авторскими.

### 7.2 Функции

| Функция | Вход | Выход |
|---------|------|-------|
| Ревью модели | Вся модель | `Finding[]` с переходом к элементу и текстом исправления |
| Контекстная подсказка | Выбранный элемент + его окружение | Объяснение типа, список допустимых связей, предложение следующего шага |
| План по описанию | Текст пользователя + каталог существующих элементов | `ModelPlan` (§5.1) + фильтрация палитры по предложенным типам |
| Документация | Модель или представление | Markdown: описание, каталог, анализ влияния |

### 7.3 Контекст запроса

Модель сериализуется в компактный JSON: элементы (`id`, тип, имя, документация),
связи (`тип`, `source`, `target`), структура представлений без геометрии. При превышении
лимита контекста передаётся подграф вокруг интересующей области (для подсказки — элемент
и его соседи на два шага; для ревью — обработка по слоям с агрегацией находок).

### 7.4 Интеграция

- Модель по умолчанию — `claude-sonnet-5`; параметр в `application.yml`.
- Ответы потоковые (SSE), структурированные результаты — через tool use со схемой,
  чтобы `Finding[]` и `ModelPlan` приходили валидными без парсинга свободного текста.
- Аудит: `AiAuditLog` фиксирует пользователя, действие, число токенов и время.
- Отключение: `workspace.ai_enabled = false` убирает панель и закрывает `/ai/**` (403).

### 7.5 Лимиты расходов

Аудит (§7.4) отвечает на вопрос «сколько потратили», но не мешает потратить лишнее.
Закрываются два разных риска — разными средствами.

**Постепенный перерасход — месячный бюджет на рабочее пространство.**
`ai_monthly_token_limit` задаёт администратор; расход считается по `AiAuditLog`
нарастающим итогом с первого числа месяца.

| Порог | Поведение |
|-------|-----------|
| 80 % | Предупреждение администратору; помощник работает |
| 100 % | `/ai/**` отвечает `429` с датой сброса; панель помощника показывает, что бюджет исчерпан |

Остальной редактор при исчерпанном бюджете работает полностью: помощник советует,
а не правит модель (FR-22), поэтому его отключение ничего не блокирует.

**Скачок — ограничение частоты и размера.** Месячный бюджет не спасает от цикла
в клиенте или зажатой кнопки: за минуты можно выбрать месяц. Поэтому:

- ограничение частоты на пользователя (запросов в минуту), `429` с `Retry-After`;
- верхняя граница контекста одного запроса — при превышении контекст сужается
  до подграфа (§7.3), а если и он велик, приходит `413` с предложением выбрать
  представление вместо всей модели;
- одновременно выполняется не более одного запроса помощника на пользователя:
  повторное нажатие отменяет предыдущий поток, а не добавляет второй.

**Видимость.** Администратор видит расход в настройках рабочего пространства:
за текущий месяц, по пользователям и по функциям помощника (ревью, подсказка, план,
документация). Это же разбиение показывает, какая функция съедает бюджет — обычно
ревью всей модели, и это повод сузить контекст, а не поднимать лимит.

## 8. Обработка ошибок

### 8.1 Формат ответа

RFC 7807 Problem Details:

```json
{
  "type": "https://archi-creator/errors/relation-not-permitted",
  "title": "Недопустимая связь",
  "status": 422,
  "detail": "Связь Assignment от Application Component к Business Actor не разрешена в ArchiMate 3.2",
  "instance": "/api/v1/models/42/relationships",
  "code": "RELATION_NOT_PERMITTED"
}
```

### 8.2 Основные сценарии

| Ситуация | Код | Поведение |
|----------|-----|-----------|
| Модель заблокирована другим пользователем | `409` | UI показывает владельца блокировки и предлагает открыть read-only |
| Конкурентное сохранение | `409` | Клиент перезагружает состояние и повторяет изменение |
| Недопустимая связь | `422` | На канве связь не создаётся, показывается причина и допустимые варианты |
| Удаление элемента со связями | `409` | Диалог со списком связей и предложением удалить их вместе |
| Импорт: битый XML | `400` | Сообщение с номером строки и позицией |
| Импорт: неизвестные типы | `200` + отчёт | Импорт выполняется, неизвестные объекты помечены как opaque, отчёт показывает их список |
| Импорт: нарушения матрицы связей, `strict_import = false` | `200` + отчёт | Модель создаётся, нарушения видны в фильтре «Замечания» (§8.3) |
| Импорт: нарушения матрицы связей, `strict_import = true` | `422` | Отказ целиком, список нарушений, модель не создаётся |
| Импорт: битая ссылка, дубль id, связь без конца | `400` | Отказ всегда, независимо от режима |
| Anthropic API недоступен | `503` | Панель помощника показывает ошибку, остальной редактор работает |
| Исчерпан месячный бюджет ИИ (§7.5) | `429` | Панель помощника сообщает о бюджете и дате сброса; редактор работает |
| Превышена частота запросов помощника | `429` + `Retry-After` | Повторить позже |
| Превышен лимит контекста ИИ | `413` | Предложение сузить область (представление вместо модели) |

### 8.3 Строгость импорта

Два разных класса проблем, которые нельзя смешивать:

| Класс | Пример | Поведение |
|-------|--------|-----------|
| **Повреждённые данные** | Невалидный XML, ссылка на несуществующий элемент, дубль идентификатора, связь без одного из концов | Отказ **всегда**, `400`, с указанием места. Импортировать наполовину нельзя |
| **Нарушения методологии** | Связь, не разрешённая матрицей ArchiMate 3.2 для этой пары типов | Зависит от `strict_import` рабочего пространства |

При `strict_import = false` (по умолчанию) модель импортируется, нарушения матрицы
попадают в отчёт импорта, в отчёт валидации и в фильтр «Замечания» дерева ([§6.6](frontend.md#66-дерево-модели-левая-панель)).
Рисовать новые недопустимые связи по-прежнему нельзя (FR-10) — ограничение действует
на редактирование, а не на приём чужих данных.

При `strict_import = true` импорт отклоняется целиком: `422`, список нарушений
с указанием пары типов и идентификатора связи, модель не создаётся. Это режим ворот
качества — например, для приёмки моделей от подрядчиков.

**Практическое замечание.** Значение по умолчанию — `false` не из мягкости: реальные
выгрузки из Visio почти всегда содержат вольности, и строгий режим сделал бы инструмент
бесполезным ровно там, где он нужен, — при наведении порядка в существующем ландшафте.
Включать строгость имеет смысл после того, как модель приведена в порядок, чтобы
не пустить регрессию обратно.

### 8.4 Логирование и наблюдаемость

- Структурированные логи (JSON) с `traceId`, пользователем и id модели.
- Spring Boot Actuator: `/actuator/health`, `/actuator/metrics`, `/actuator/prometheus`.
- Отдельные метрики: длительность импорта/экспорта, размер модели, число обращений к ИИ
  и потраченные токены, частота конфликтов блокировки.

## 11. Git-интеграция и формат хранения

Решение по открытым вопросам 2 и 3, принято 22.09.2026.

### 11.1 Роль Git: журнал и ревью, а не распределённое редактирование

Git используется как **читаемая история и инструмент ревью архитектурных изменений**,
а не как механизм параллельной работы. Причина прямая: модель находится под блокировкой
у одного архитектора (FR-05), поэтому ежедневный сценарий «двое правят одно и то же
одновременно» отсутствует по построению, а именно он и делает слияние графов дорогим.

**Источником правды остаётся PostgreSQL.** Репозиторий — производная величина,
которая всегда может быть перестроена из базы. Это снимает целый класс проблем
«две правды разошлись».

Что это даёт: `git log` и `git blame` по каждому элементу, diff между любыми двумя
состояниями, ревью изменений через merge request в существующем GitLab банка,
восстановление любого прошлого состояния, аудит «кто и когда добавил эту интеграцию».

### 11.2 Формат: разложенный YAML

Один файл `.archimate` в репозитории не годится: 4 437 строк XML, где перемещение
одного элемента даёт diff на пол-файла, а любые две правки пересекаются. Поэтому
модель раскладывается по файлам.

```
<репозиторий рабочего пространства>/
  .gitattributes
  models/
    hamkorbank-it-landshaft-as-is.6f2c91d0/       слаг имени + 8 hex от ModelId
      model.yaml                                  метаданные модели
      folders.yaml                                дерево папок
      elements/
        application/iabs.488a7b5a.yaml
        application/kart-info-servis.8aea7374.yaml
        technology/oracle-19c.b7a8e84d.yaml
        business/fizicheskoe-litso.ccd4f847.yaml
      relations/
        serving.3399b633.yaml
        composition.207a1b4e.yaml
      views/
        01-kontekst-as-is-kak-narisovano-v-visio.f11fbcb8.yaml
```

Каталог модели находится по суффиксу `.<8 hex>` и при переименовании модели не
меняется: переименование — одна строка в `model.yaml`, а не перемещение всех файлов.

**Принципы именования и раскладки**

| Решение | Почему так |
|---------|-----------|
| Имя файла — `<слаг>.<8 hex от id>.yaml`, слаг транслитерируется в латиницу | В `ls` и в списке изменений merge request видно, что за элемент, без открытия файла. Короткий id снимает коллизии имён. Транслитерация — потому что кириллические имена файлов доставляют проблемы в смешанном CI и на разных файловых системах |
| Принадлежность папке — **поле внутри файла**, а не каталог | Переименование папки меняет одну строку в `folders.yaml`, а не двигает 72 файла. Каталоги `elements/<слой>/` нужны только чтобы не держать 400 файлов в одной директории |
| Порядок — разреженное числовое поле `position` (шаг 1000) | Порядок узлов обязателен для lossless round-trip (§3.4, п. 3). Разреженность означает, что вставка элемента не перенумеровывает соседей и не порождает diff на всю папку |
| Идентификаторы — из `.archimate`, буквально | Ключ слияния (§11.4) и единственное, что не меняется при переименованиях |
| Представление — один файл целиком | Представление правится как единое целое; дробить геометрию на файлы смысла нет, а diff по одному виду остаётся коротким |
| В заголовке файла связи — комментарий с именами концов | Без него `git log -p` по связям нечитаем: одни идентификаторы |

**Пример элемента** (`elements/application/iabs.2ae470c0.yaml`, данные настоящие):

```yaml
id: id-2ae470c0df71095e61b6d059
type: ApplicationComponent
name: IABS
folder: f-master-sistemy
position: 12000
properties:
  - key: source
    value: "Hamkorbank ALL.vsdx, страницы as is"
  - key: owner
    value: FIDO
  - key: db
    value: Oracle 19c
```

**Пример связи** (`relations/serving.3399b633.yaml`):

```yaml
# IABS → Интернет банкинг ФЛ
id: id-3399b633bae72b9c082315d1
type: ServingRelationship
source: id-2ae470c0df71095e61b6d059
target: id-d897941376aa1f03a866016b
folder: f-relations
position: 24000
```

**Неподдержанные сущности** (FR-03) переносятся без потерь: их исходный XML лежит
в поле `raw_xml` блочным скаляром. Без этого цикл БД → Git → БД ломал бы round-trip.

**Формат обратим, а не только читаем** (решение этапа 7a). Из дерева собирается
тот же документ модели и те же байты `.archimate`, что снимок версии, — на этом
стоит восстановление очищенного снимка (FR-46). Поэтому в формате есть то, что
читателю обычно не видно:

- узел пишется ключами `id`, `type`, `name` (у связей ещё `source`, `target`)
  и отображением `attributes` с остальными атрибутами в порядке файла; тип — без
  префикса `archimate:`, чужой префикс (`canvas:CanvasModel`) остаётся;
- представление — один файл: узлы внутри — списки `children` и `connections`
  с геометрией `bounds: {x: 20, y: 60, width: 150, height: 60}`; у них в своих
  ключах только `id` и `type`, `name` — в `attributes`, потому что Archi пишет его
  у узлов представления где придётся;
- порядок атрибутов и содержимого, отличный от того, что пишет Archi, хранится
  служебными списками `attribute_order` и `content_order`. На эталонной модели
  их нет ни в одном файле; появляются у файлов из сторонних инструментов;
- значения без своего вида — `values` с тегом, атрибутами и текстом.

**«Сортировка свойств» — фиксированный порядок, а не алфавит.** Порядок `property`
в Archi значим и входит в round-trip; алфавит сломал бы цикл БД → Git → БД.
Детерминированность держит то, что порядок берётся из документа.

**`position` наследуется из предыдущего коммита.** Снимок версии несёт плотный
порядок документа, а не разреженный `sort_order` базы. Поэтому позиция объекта
берётся из того же файла в HEAD; новые встают в промежутки (`500` перед `1000`),
и только когда места нет — папка нумеруется заново шагом 1000.

**Детерминированность писателя** — обязательное требование, равное по важности §9.1:
фиксированный порядок ключей, сортировка свойств, LF, отсутствие якорей и переносов
по ширине. Проверяется golden-file тестом по образцу §9.1: экспорт → экспорт без
изменений даёт побайтово тот же результат. Недетерминированный писатель превратил бы
каждый коммит в шум.

**Формат версионируется** (`format_version` в `model.yaml`) и может эволюционировать.
Гарантией совместимости с внешним миром остаётся `.archimate` (FR-02), а не он.

**Сгенерированный `.archimate` в репозиторий не кладётся.** Он производный, даёт шумный
diff на каждое изменение, удваивает объём и создаёт вторую правду в одном дереве.
Вместо этого — эндпоинт экспорта (§5) и CI-задача, собирающая `.archimate` артефактом
на теге версии.

### 11.3 Направление обмена

| Этап | Что работает | Сложность |
|------|--------------|-----------|
| **7a** | Односторонний экспорт: сохранение модели создаёт коммит | Низкая: пишет только сервер, только из-под блокировки, конфликтов нет по построению |
| **7b** | Импорт ссылки (коммита, тега, ветки) как новой версии модели | Средняя: разбор дерева, сверка с текущим состоянием, отчёт об изменениях, применение одной транзакцией |
| **7c** | Предложения через ветку и merge request, слияние при разошедшейся базе | Высокая: слияние по сущностям (§11.4) |

Коммит на этап 7a: автор — архитектор (соответствие Keycloak → git identity задаётся
в настройках рабочего пространства), сообщение — комментарий к сохранению, трейлеры
`Archi-Model-Id` и `Archi-Version` для обратной связи с `ModelVersion`.

Если HEAD ветки сдвинулся, пока модель была под блокировкой, сервер **не** коммитит
поверх: сохранение в БД проходит, экспорт помечается как расхождение и требует импорта
(7b) или слияния (7c). Молча перезаписывать чужой коммит нельзя.

Расхождением на этапе 7a считается не любой чужой коммит, а **коммит, тронувший
каталог модели** (последний коммит каталога несёт чужой `Archi-Model-Id` или его нет),
и **переписанная история** (последний коммит сервера больше не предок HEAD). Правка
README или другой модели расхождением не является: наш коммит ложится сверху
fast-forward'ом и ничего не перезаписывает. Иначе одна правка README остановила бы
выгрузку всех моделей до этапа 7c.

**Доставка — через outbox** ([`ADR-0003`](../spec/adr/0003-event-publishing.md)).
Версия попадает в таблицу `outbox_event` той же транзакцией, что фиксируется;
фоновый обработчик публикует версии по порядку внутри модели, `git_sha` пишется
в версию вместе с закрытием записи. Падение между push и этой записью повтор находит
по трейлерам и второго коммита не создаёт. Недоступный репозиторий откладывает
публикацию с нарастающей паузой; `POST /models/{id}/git/push` догоняет очередь
модели сейчас.

**Импорт по ссылке** (этап 7b, [`UC-IXC-006`](../spec/application/interchange/usecases/pull-model-from-git.md))
идёт в два шага. Отчёт: ссылка разрешается как в `git rev-parse` (тег раньше ветки,
коммит — и сокращённым), каталог модели собирается обратно в документ тем же читателем,
что восстанавливает снимок, и сравнивается с текущим содержимым базы по объектам —
папкам, элементам, связям, представлениям, с перечнем изменённых полей. Отчёт ничего
не пишет. Применение принимает из отчёта коммит и отпечаток текущего содержимого:
применяется ровно увиденное — ветка могла уехать, модель могла измениться, и тогда
нужен новый отчёт. Замена содержимого, новая версия и закрытие сессии импорта — одна
транзакция; отказ оставляет только сессию `REJECTED` с причиной.

Импорт **головы ветки привязки** разрешает расхождение: старые версии модели, стоявшие
в очереди публикации, пропускаются (их коммит откатил бы ветку), а новая версия
получает идентификатор головы без нового коммита — её содержимое там уже лежит. После
этого чужая правка каталога, уже вошедшая в последний опубликованный коммит модели,
расхождением не считается: переписывать нечего.

### 11.4 Слияние: по сущностям, а не по тексту

Ключевое решение: **Git никогда не сливает наши файлы текстом.** В `.gitattributes`
для `models/**` слияние отключено, поэтому YAML с маркерами `<<<<<<<` не возникает
в принципе. Слияние выполняет приложение, и работает оно не со строками, а с сущностями
по стабильному `id`.

Это радикально проще, чем звучит «слияние графов». Берём три состояния — общий предок
(коммит merge-base), «наше» и «их» — и сравниваем поэлементно:

| Ситуация | Разрешение |
|----------|-----------|
| Поле изменено только в одной ветви | Берётся изменённое, без вопросов |
| Элемент добавлен только в одной ветви | Добавляется |
| Одно и то же поле изменено в обеих, значения разные | Конфликт, выбор архитектора по полю |
| Элемент удалён в одной, изменён в другой | Конфликт с явным выбором «удалить» / «оставить с правками» |
| Удалён элемент, у которого есть связи на другой стороне | Связи удаляются вместе, попадают в отчёт |
| Геометрия одного объекта представления двигалась в обеих ветвях | Представление берётся целиком с одной стороны: попиксельное слияние бессмысленно |
| Обе ветви вставляли в одну папку | Оба набора сохраняются, порядок — сортировка по `position`, совпадения разводятся перенумерацией |

Переименование и перемещение **не конфликтуют** с правкой других полей того же элемента,
потому что ключ — идентификатор, а не имя и не путь. Это прямое следствие §11.2.

Результат слияния показывается на холсте до применения: добавленное зелёным, удалённое
красным, изменённое — подсветкой, конфликты — списком с выбором. Применяется одной
транзакцией как новая версия модели.

**Как это устроено** (этап 7c, [`UC-IXC-007`](../spec/application/interchange/usecases/merge-model-branch.md)).
«Наше» — текущее содержимое модели в базе, «их» — каталог модели в коммите ветки
предложения, база — каталог в общем предке коммита ссылки и коммита последней
опубликованной версии. Поля объекта — каждый атрибут отдельно, `documentation`,
`properties` списком (порядок значим), `raw_xml`, родительская папка, у представления —
диаграмма целиком. Порядок детей конфликтом не бывает: основа — порядок ветви, которая
его меняла, добавленное другой ветвью встаёт после своего соседа. Каскад — связь без
конца, узел представления без элемента, ребро без концов — следствие, а не конфликт,
и тоже попадает в отчёт. Отчёт принимает выборы по конфликтам и пересчитывает
результат: так интерфейс показывает итог выбора до применения.

Слитый коммит записывается за моделью. Его правки публикация больше не считает
расхождением, а если ветка привязки его не содержит, он становится вторым родителем
нашего коммита: ветка merge request'а оказывается предком ветки привязки, и GitLab
закрывает merge request сам — без текстового слияния и без переписывания истории.
Слияние головы ветки привязки снимает расхождение, как импорт по ссылке.

### 11.5 Реализация

- **JGit**, без внешнего бинарника `git`: одна зависимость, работает в контейнере как есть.
  Адаптер — в `archi-bootstrap` (`bootstrap.git`), как Batik: отдельный модуль менял бы `ADR-0001`.
- Один репозиторий на рабочее пространство, каталог на модель. Bare-клон кэшируется
  на сервере (`archi.git.cache-dir`), `fetch` перед каждой операцией. Коммит собирается
  в памяти, без рабочего дерева, и уходит push'ем с ожидаемой прежней головой ветки.
- Доступ — токен в переменной окружения сервера ([§10.3](archi-creator.md#103-профили-и-конфигурация));
  привязка пространства хранит не токен, а ссылку на неё: `env:ARCHI_GIT_TOKEN`.
- `.archimate` на теге собирает CI-задача репозитория выгрузки: образец —
  [`deploy/git/gitlab-ci.yml.example`](../deploy/git/gitlab-ci.yml.example).
- Ограничение по объёму: на модели вашего масштаба (402 элемента) это около 450 файлов —
  для Git ничто. Порог, после которого `git status` становится заметным, — примерно
  20 000 файлов на репозиторий; это ориентир для разделения рабочих пространств.
