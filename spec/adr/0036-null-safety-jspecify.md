# ADR-0036 — Null-безопасность: разметка JSpecify и NullAway при компиляции

## Статус

Принято 2026-10-22 по итогам этапа 18 ревью кода (`docs/plans/code-review-fixes.md`, нарушение D-14).
Дополняет `ADR-0027`: тот решил, что отсутствие значения — `null`, а не `Optional`, и оставил D-14 открытым —
проверка значений в конструкторе не заменяет статического анализа. Приводит проект к §6.4 внутреннего стандарта
`java-spring-code-guidelines-v2.md` (версия 3.0).

## Контекст

После `ADR-0027` необязательное значение в домене, сценариях и адаптерах — `null`, и о том, где он допустим,
говорил только Javadoc. Компилятор этого не видел: разыменование необязательного поля или передача `null` туда,
где его не ждут, всплывали бы в работе. Spring Framework 7 и Boot 4 размечены JSpecify, и без своей разметки
контракт их сигнатур тоже не проверялся.

Против разметки был довод границы модулей: в доменных модулях единственная зависимость — `java-uuid-generator`,
и это держат enforcer и `HexagonalArchitectureTest`.

## Рассматриваемые варианты

**1. Отступление: проверки в конструкторе и SpotBugs.** Ничего не меняет в коде, но SpotBugs ловит разыменование
`null` только высокой уверенности, а контракт «здесь бывает `null`» по-прежнему живёт в Javadoc.

**2. Разметка без анализатора.** Аннотации без проверки — документация, которая расходится с кодом молча.

**3. JSpecify во всех модулях и NullAway как ошибка компиляции.**

## Решение

Вариант 3.

- `org.jspecify:jspecify` подключён родителем во все модули, домен включительно: аннотации без кода и без своих
  зависимостей. В домене это вторая разрешённая зависимость после генератора UUID.
- Каждый пакет основного кода — `package-info.java` с `@NullMarked`: всё не-`null` по умолчанию, необязательное
  значение помечается `@Nullable` — поле, компонент record, параметр, результат. Сплошность разметки проверяет
  `NullMarkedPackagesTest` по исходникам всех модулей.
- NullAway (Error Prone) проверяет основной код проекта при компиляции, `AnnotatedPackages` — корневой пакет
  проекта; срабатывание — ошибка компиляции. Подавлений (`@SuppressWarnings("NullAway")`) нет.
- Тесты NullAway не проверяет: они делят пакеты с основным кодом, а `null` в тесте — способ проверить отказ.
- Прочие проверки Error Prone выключены: их область держат PMD и SpotBugs, включение — отдельное решение.

## Последствия

- Необязательность видна в сигнатуре и проверяется компилятором; Javadoc «`null` — нет значения» остаётся
  объяснением смысла, а не единственным контрактом.
- `Map.get` по ключу, который есть по построению, пишется явно (`getOrDefault`, `instanceof`-шаблон,
  `Objects.requireNonNull` там, где наличие и есть контракт) — анализатор не видит инвариантов агрегата.
- `equals` размеченных классов принимает `@Nullable Object`.
- Компилятору в процессе Maven нужны `--add-exports` модуля `jdk.compiler` — `.mvn/jvm.config`.
- Новый пакет без `package-info.java` с `@NullMarked` роняет сборку.
