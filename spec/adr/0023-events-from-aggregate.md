# ADR-0023 — События создаёт агрегат, Domain Service не вводится

## Статус

Принято 2026-10-14 по итогам этапа 0 ревью кода (отклонение D-06). Дополняет
[`ADR-0003`](0003-event-publishing.md): тот решает, **как событие доставляется**,
этот — **кто его создаёт**. Отступает от внутреннего стандарта
`java-spring-code-guidelines-v2.md` в §3.3.6.6 и приложении D (№ 6).

## Контекст

Стандарт для гексагональной архитектуры с DDD требует: ни один слой выше домена
не вызывает бизнес-методы агрегата напрямую, только через Domain Service; основной
способ создания события — Domain Service создаёт и возвращает его. Накопление событий
в агрегате стандарт отводит варианту с CQRS. Обоснование правила — если обработчик
вызовет `order.pay()` напрямую, событие не родится, и интеграция сломается молча.

В проекте:

- события накапливает агрегат: бизнес-метод кладёт событие в список, application-сервис
  забирает их `pullEvents()` после записи и публикует (`ArchitectureModel`, `ImportSession`,
  `AdvisorSession`, `TokenBudget`); способ один во всех трёх контекстах;
- application-сервисы вызывают бизнес-методы агрегатов напрямую
  (`ViewService` — `view.placeElement(model, …)`, `view.connect(model, …)`);
- доменные службы без состояния есть там, где правило не принадлежит одному агрегату:
  `NestingRules`, `RelationMatrix`, `EntityMerge`.

## Рассматриваемые варианты

**1. Ввести Domain Service на каждый агрегат.** Каждый бизнес-метод получает обёртку,
которая его вызывает; application-сервис зовёт обёртку. Риск, ради которого правило
существует, при этом не снимается лучше, чем сейчас, — событие и так рождается внутри
бизнес-метода, — а слой удваивает число мест, куда смотреть при правке.

**2. Записать нынешнюю схему.** Событие — часть бизнес-метода агрегата, обойти его
вызовом «в обход» нельзя: другого способа изменить состояние агрегат не даёт.

## Решение

Вариант 2.

- **Событие создаёт бизнес-метод агрегата**, в той же операции, что меняет состояние,
  и кладёт в список агрегата. Application-сервис после записи забирает события
  `pullEvents()` и отдаёт порту публикации; доставка — по `ADR-0003` (после коммита,
  `ModelVersionCommitted` — через outbox).
- **Application-сервис вызывает бизнес-методы агрегата напрямую.** Сервис координирует:
  загрузка, проверка роли, вызов, запись, публикация. Правила — в агрегате.
- **Доменная служба** (stateless, без Spring) заводится, когда правило не принадлежит
  одному агрегату или требует каталога: допустимость связи, вложенность, слияние трёх
  состояний. Её не заводят как обязательную прослойку перед агрегатом.
- Агрегат, которому нужен другой агрегат для проверки (`View` и `ArchitectureModel`),
  получает его аргументом бизнес-метода, а не ссылкой в поле.
- **Исключение — событие о факте внешней системы.** Если событие сообщает не о переходе
  состояния агрегата, а о том, что состоялось во внешней системе (коммит записан в Git),
  его создаёт application-сервис после транзакции, в которой записан итог. Такое событие
  перечисляется поимённо в проверке сборки с причиной; сейчас оно одно —
  `GitSnapshotCommitted`: публикуется, даже когда привязка не записывается
  (`GitBinding` не `writable`), поэтому принадлежать бизнес-методу привязки не может.

## Уточнение 2026-10-14

При составлении плана действий (`docs/plans/otstupleniya-ot-standarta.md`) выяснилось,
что первая редакция ошибалась: два события создавали application-сервисы.
Решение владельца по каждому:

- `ModelVersionCommitted` (`VersionService`) — **переносится в агрегат**: его создаёт
  фабрика `ModelVersion.commit` и возвращает вместе с версией (`ModelVersion.Committed`).
  Версия — неизменяемая запись без списка событий, поэтому событие возвращается, а не
  накапливается; прежней фабрики `next`, создававшей версию без события, больше нет.
  Это звено outbox (`ADR-0003`): событие, потерянное при прямом создании версии,
  оставило бы дыру в журнале Git — ровно тот риск, ради которого стандарт ввёл правило.
- `GitSnapshotCommitted` (`GitPublishingService`) — **остаётся в сервисе** по исключению
  выше.

## Последствия

- Находки ревью «агрегат вызван не из Domain Service» не заводятся. Заводятся: бизнес-правило
  в application-сервисе, изменение состояния агрегата без события там, где событие
  объявлено в `spec/domain/<bc>/events.yaml`, публикация событий в обход `pullEvents()`.
- Что событие рождается вместе с переходом состояния, держат юнит-тесты агрегатов
  (`pullEvents()` после бизнес-метода).
- Что событие создаётся только в домене, держит ArchUnit: конструктор события
  вызывается из классов `..domain..` своего контекста; исключения — поимённо.
