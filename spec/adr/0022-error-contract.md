# ADR-0022 — Контракт ошибок: Problem Details со строковым кодом

## Статус

Принято 2026-10-14 по итогам этапа 0 ревью кода (отклонения D-03, D-04). Записывает
решение, по которому API работает со второго этапа (`docs/backend.md` §8.1), и отступает
от внутреннего стандарта `java-spring-code-guidelines-v2.md` в §4.3.3 и приложении D
(№ 13, № 17).

## Контекст

Стандарт задаёт тело ошибки `{code, message, timestamp, path, traceId}` с шестизначным
числовым `code`; формат Problem Details (RFC 9457) допускает только по ADR и при условии,
что `code` идёт расширенным свойством. Неожиданная ошибка по стандарту — `400` с кодом
`999999`: `500` клиенту не отдаётся.

В проекте:

- все четыре обработчика (`ModelingProblemHandler`, `InterchangeProblemHandler`,
  `AdvisorProblemHandler`, `CommonProblemHandler`) отвечают `application/problem+json`;
  `code` — расширенное свойство, `instance` — путь запроса; `traceId` в тело не входит —
  он приходит заголовком `X-Trace-Id` на каждом ответе (`RequestCorrelationFilter`),
  ошибочном и успешном, и тем же значением пишется в логи;
- коды строковые: якорь инварианта (`INV-MDL-006`) или имя бизнес-отказа
  (`RELATION_NOT_PERMITTED`, `MDL_NOT_FOUND`); они — константы `ModelingCodes`,
  `InterchangeCodes`, во фронтенде — `src/api/codes.ts`, и клиент ветвится по ним;
- выгрузка в OEF, не прошедшая официальную XSD, отвечает
  `500 IXC_OEF_SCHEMA_VIOLATION` — так записано в UC-IXC-005.

## Рассматриваемые варианты

**1. Перейти на тело стандарта и числовые коды.** Цена: переписать контракты трёх
контекстов в `spec/contracts/`, обработчики, фронтенд и тесты; выгода — единый формат
с сервисами, которые этот API не вызывают. Числовой код теряет главное свойство
нынешнего: по `INV-MDL-006` видно, какое правило нарушено, без справочника.

**2. Оставить Problem Details со строковым кодом.** Условие стандарта для Problem Details
(`code` расширенным свойством) уже выполнено.

## Решение

Вариант 2.

- **Тело ошибки — RFC 9457** (`type`, `title`, `status`, `detail`, `instance`) плюс
  обязательное расширение `code`; дополнительные поля — по ситуации,
  как описано в контрактах (`lockOwner`, `relationships`, `permitted`).
- **`traceId` — заголовок `X-Trace-Id`, а не поле тела:** он нужен и на успешном
  ответе (жалоба «сохранилось не то» — тоже повод искать в логах), а поле было бы
  только у ошибок. Заголовок описывается в контрактах `spec/contracts/`.
- **Код — строка** из закрытого набора констант `*Codes`; это контракт API, текст
  `detail` — перевод по `Accept-Language`, клиент на него не опирается.
- **`500` отдаётся только на дефект сервера, о котором клиенту нужно знать по коду** —
  сейчас два случая: `IXC_OEF_SCHEMA_VIOLATION` — сервер собрал файл, нарушающий
  официальную схему, и `MDL_SNAPSHOT_CORRUPTED` — снимок версии в хранилище повреждён
  и не распаковывается (добавлено 2026-10-16, этап 5 ревью кода). Это не ошибка запроса, и `400` ввёл бы клиента в заблуждение —
  повтор того же запроса даст тот же отказ по вине сервера.
- **Неожиданное исключение** не раскрывает ни стека, ни SQL, ни имён классов — это
  требование стандарта сохраняется полностью; каким кодом и статусом оно отвечает,
  проверяет этап 11 ревью.

## Последствия

- Находки ревью по форме тела ошибки и числовым кодам не заводятся; по раскрытию
  внутренних деталей — заводятся.
- Новый отказ — константа в `*Codes`, ключ сообщения в обоих файлах локали и строка
  в контракте `spec/contracts/<bc>/rest-api.openapi.yaml`.
