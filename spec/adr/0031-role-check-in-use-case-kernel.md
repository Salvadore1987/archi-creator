# ADR-0031 — Роль операции проверяет ядро сценария, а не `@PreAuthorize`

## Статус

Принято 2026-10-21 по итогам этапа 12 ревью кода (`docs/review/12-bootstrap-security.md`, находка 12-12,
отклонение D-21). Отступает от внутреннего стандарта `java-spring-code-guidelines-v2.md` (версия 3.0)
в §4.13.2 и §6.11 №5 (авторизация бизнес-операций — `@PreAuthorize` на use case в `application`).
Записывает решение, действующее с этапа 2.

## Контекст

Стандарт вешает правило доступа аннотацией Spring Security на метод сценария application-слоя.
В проекте в application-слоях Spring нет вовсе: транзакция — порт `UnitOfWork` (`ADR-0024`),
а `maven-enforcer-plugin` запрещает `org.springframework*` в `domain` и `application` всех трёх
контекстов. Перечень «операция → роли» — нормативная таблица `authorization` в `spec/nfr/<bc>.yaml`.

Нужно, чтобы роль проверялась в одном месте для каждого входа в сценарий: REST, фоновый проход
очереди, мосты между контекстами.

## Рассматриваемые варианты

**1. `@PreAuthorize` на входных портах.** Тянет Spring Security в application-слой и ломает границу,
которую держит сборка; правило в SpEL-строке не сверить с таблицей спецификации, а вход без
прокси Spring (вызов сценария из другого сценария, тест на фейках) обходит его молча.

**2. Матчеры URL в цепочке безопасности.** Правило живёт у одного адаптера: второй вход
в тот же сценарий его не видит, и таблица ролей дублируется путями.

**3. Ядро сценария проверяет роль по закрытому перечню операций.** Handler называет операцию,
ядро контекста (`ModelingKernel`, `InterchangeKernel`, `AdvisorKernel`) проверяет роль автора
до любой работы — по перечислению операций, совпадающему с таблицей спецификации.

## Решение

Вариант 3.

- Роль проверяется на границе use case'а ядром контекста, первой — до чтения данных, разбора
  ввода и внешних вызовов. Отказ — исключение контекста с кодом из `*Codes`.
- Перечни операций (`Operation`, `InterchangeOperation`, `AdvisorOperation`) совпадают с таблицами
  `authorization` спецификации; это проверяет `OperationTablesTest`.
- Цепочка безопасности отвечает только на «вошёл ли»: API — по токену, Actuator — роль `ADMIN`
  на административных эндпоинтах. Ролей операций в матчерах URL нет.
- `@PreAuthorize` и `@EnableMethodSecurity` не вводятся.

## Последствия

- Находка ревью «нет `@PreAuthorize`» не заводится.
- Системные входы без актора (проход очереди Git, восстановление снимка) роль не проверяют —
  её проверяет вызывающий; такие входы помечены в своих входных портах.
- Новая операция — строка в таблице `authorization` спецификации и значение перечня операций
  в одном коммите, иначе падает `OperationTablesTest`.
