# ADR-0035 — Уязвимости ищет Trivy по образу, образ из CI не публикуется

## Статус

Принято 2026-10-22 по итогам этапа 17 ревью кода (`docs/review/17-sborka-konteiner-ci.md`, находка 17-12,
отклонение D-25). Отступает от внутреннего стандарта `java-spring-code-guidelines-v2.md` (версия 3.0)
в §4.16.5 (сканер зависимостей — `dependency-check-maven`) и §4.16.6 (стадии `publish` и `deploy`).

## Контекст

Стандарт называет два сканера: OWASP `dependency-check-maven` для зависимостей с отказом при CVSS ≥ 7 и Trivy
для образа. Конвейер стандарта заканчивается публикацией образа в реестр с ветки `main` и деплоем.

В проекте до этапа 17 не было ни одного сканера — разовый прогон Trivy нашёл в jar Tomcat с CRITICAL и Jackson
с HIGH. Публикации нет: состав по §10.1 собирает образ на внутреннем сервере банка из jar
(`docker compose build`), реестра образов у проекта нет.

## Рассматриваемые варианты

**1. `dependency-check-maven` в сборке и Trivy по образу — как в стандарте.** Два сканера с двумя базами
уязвимостей отвечают на один вопрос про одни и те же jar: Trivy находит библиотеки внутри образа сам.
`dependency-check` качает базу NVD; без ключа API загрузка идёт десятки минут и упирается в лимиты,
с ключом — секрет в CI ради дублирующей проверки. Кэш базы между прогонами — ещё одна движущаяся часть.

**2. Только Trivy по собранному образу.** Одна проверка видит и библиотеки jar, и пакеты ОС базового образа,
и секреты в слоях; база Trivy качается за секунды без ключа. Сканируется ровно то, что уходит в бой,
а не дерево зависимостей Maven, которое с образом может разойтись (исключения, слои, базовый образ).

**3. Реестр образов и деплой из CI.** Нужна среда, которой у проекта нет: развёртывание — состав на одном
сервере, сборка образа — там же из того же jar, что прошёл конвейер.

## Решение

Вариант 2; стадий `publish` и `deploy` в конвейере нет.

- Работа `image` после `docker build` запускает Trivy (`--scanners vuln,secret --severity HIGH,CRITICAL
  --ignore-unfixed --exit-code 1`): уязвимость уровня HIGH и выше, у которой есть исправленная версия, и любой
  найденный секрет роняют конвейер. Образ сканера закреплён по дайджесту.
- Уязвимость без исправления конвейер не роняет: сделать с ней нечего, а красный конвейер без выхода
  приучает его не смотреть.
- Уязвимая версия из BOM Spring Boot закрепляется поверх BOM в родительском `pom.xml` до выпуска Boot с исправлением;
  компонент базового образа, не нужный приложению, удаляется в `Dockerfile`.
- Состав зависимостей запущенного приложения отдаёт `/actuator/sbom` — по нему новая уязвимость сверяется
  с работающим образом без пересборки.

## Последствия

- Находки ревью «нет `dependency-check-maven`» и «нет стадий публикации и деплоя» не заводятся.
- Новая уязвимость в зависимости роняет конвейер и без изменений в коде — это ожидаемо: исправление —
  версия поверх BOM или свежий базовый образ, а не исключение из сканирования.
- Появится реестр образов — публикация с `main` добавляется отдельной работой после `image`, и решение
  пересматривается в части §4.16.6.
