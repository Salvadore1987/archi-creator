# ADR-0018 — Сессия правки живёт в браузере, на сервер уходит при сохранении

## Статус

Принято 2026-10-09, этап 3. Следует из FR-35, FR-05, FR-06 и NFR-05.

## Контекст

История изменений обязана работать на любую глубину сессии, отмена — возвращать
модель в прежнее состояние, а отмена *за* точку сохранения — считаться
несохранённым изменением (`UI-017`, [§6.9](../../docs/frontend.md#69-история-изменений)).
Пока модель под блокировкой (`INV-MDL-006`), её правит один архитектор, и правки
«живут локально до явного сохранения, создающего версию»
([§6.8](../../docs/frontend.md#68-редактирование-дерева)).

API этапа 2 — команды по одной: создать элемент, переименовать, перенести,
удалить, сохранить геометрию. Каждая меняет текущее состояние в базе сразу,
а версия фиксируется отдельной командой `POST /models/{id}/versions`.

Два способа соединить историю с такими командами:

1. **Каждая правка — сразу команда на сервер, отмена — обратная команда.**
   Отмена удаления тогда — создание заново, а создание в API этапа 2 даёт новый
   `archi_id`, новую позицию в папке и теряет остаток XML (`ADR-0017`). Цикл
   «удалил → отменил» меняет файл, хотя пользователь вернул всё как было. Это
   нарушает обещание round-trip там, где пользователь его не ждёт нарушенным.
2. **Правки копятся в документе браузера, на сервер уходят при сохранении.**
   Удаление с отменой до сохранения серверу не видно вовсе, остаток XML на месте.

## Решение

Второй вариант.

- **Документ модели в браузере** — нормализованная копия дерева и открытых
  представлений. Правка — операция истории из обратимых изменений: у каждого
  изменения есть применение к документу, обратное изменение и серверная команда.
- **Сохранение = синхронизация + версия.** Клиент переводит сервер из состояния
  «точка сохранения» в состояние «текущая позиция»: прямые команды вперёд по
  истории, обратные — назад, затем `POST /models/{id}/versions`. Ветка истории,
  отброшенная новой правкой после отмены, оставляет очередь обратных команд для
  уже отправленного — она уходит первой.
- **Идентификаторы новых объектов задаёт клиент.** Команды создания принимают
  необязательные `id` (UUIDv7) и `archiId` (`id-<32 hex>`); сервер проверяет
  формат и уникальность в модели. Так ссылки в истории не переписываются после
  ответа сервера, а отмена удаления, уже отправленного на сервер, возвращает
  объект с тем же `archi_id`.
- **Сбой посреди синхронизации** не откатывает документ: невыполненные команды
  остаются в очереди, пользователь видит причину и решает — повторить
  сохранение, отменить правку или сбросить несохранённое перечитыванием модели.

## Последствия

- Отмена и повтор до сохранения — без сети и без потерь.
- Отмена удаления, уже сохранённого на сервере, возвращает объект с прежними
  `id` и `archi_id`, но не возвращает остаток XML удалённой строки и позицию
  в папке: строка создаётся заново в конце родителя. Это видно в диффе
  выгрузки и записано здесь, а не замалчивается.
- Серверу нужны: `id`/`archiId` в командах создания и размещение ребра
  существующей связи — иначе отмена удаления узла не вернёт его рёбра.
- Пока сохранение не нажато, другой пользователь видит последнюю
  синхронизированную модель — и это ожидаемо: модель под блокировкой автора.
- Закрытие вкладки браузера с несохранёнными правками теряет их; браузер
  предупреждает об этом стандартным диалогом `beforeunload`.
