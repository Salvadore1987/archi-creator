# ADR-0016 — Фронтенд живёт внутри `archi-bootstrap`, а не отдельным модулем реактора

## Статус

Принято 2026-09-29 при закрытии этапа 0.

## Контекст

[`ADR-0001`](0001-maven-multi-module.md) зафиксировал 17 проектов в реакторе.
Фронтенда среди них нет: на момент решения не было ни `package.json`,
ни исходников React. Этап 0 требует каркас React + Vite, и вопрос «где он
лежит» приходится решать до того, как появится первый файл.

Существенно то, что фронтенд **не участвует в графе зависимостей Java**.
Его результат — статика в `target/classes/static`, которую отдаёт
`archi-bootstrap`. Ни один Java-модуль от него не зависит и зависеть не может:
между ними нет ни классов, ни API, только каталог с файлами.

## Решение

Фронтенд лежит в `archi-bootstrap/src/main/frontend` и собирается
`frontend-maven-plugin` в том же модуле. Реактор остаётся семнадцатипроектным,
jar — одним.

```
archi-bootstrap/
  src/main/frontend/       package.json, vite.config.ts, src/
  src/main/java/           точка входа и security
  src/main/resources/      application.yaml, db/migration/
  target/classes/static/   ← сюда кладёт сборку Vite
```

Профиль `frontend` в `archi-bootstrap/pom.xml` включён по умолчанию
и отключается `-P '!frontend'` — сборка бэкенда не должна требовать Node
там, где фронтенд не менялся.

## Последствия

**Хорошие.** `ADR-0001` не переписывается: «модуль = слой × bounded context»
остаётся верным утверждением, а не правилом с исключением. Сборка `mvn package`
в корне даёт готовый jar со статикой внутри — ровно то, что обещает
[§10.2](../../docs/archi-creator.md#102-сборка). Путь от правки `.tsx`
до jar'а — одна команда.

**Плохие.** `archi-bootstrap` перестаёт быть маленьким: в нём и точка входа,
и безопасность, и миграции, и весь фронтенд. Сборка модуля дольше на время
`npm ci && npm run build`; смягчено профилем, но по умолчанию платится.
Для фронтенд-разработчика корень проекта неочевиден — он на два уровня
глубже, чем ожидается.

**Обратимость.** Высокая, пока в дело не вошёл CI чужой команды: перенос
каталога в отдельный модуль `archi-frontend` — это `git mv`, новый `pom.xml`
с `maven-resources-plugin` и одна зависимость в `archi-bootstrap`. Решение
сознательно принято как дешёвое в отмене.

## Отвергнутая альтернатива

**Восемнадцатый модуль реактора `archi-frontend`.** Правильнее с точки зрения
симметрии: у фронтенда свой `pom.xml`, свой `target`, своя строка в реакторе.
Отвергнуто по двум причинам. Первая: модуль-пустышка вокруг `npm` не даёт
Maven ничего, кроме места для плагина, — зависимостей у него нет, артефакт
он производит нестандартный (jar с `static/`), и `archi-bootstrap` всё равно
обязан его распаковать. Вторая: `ADR-0001` перечисляет 17 проектов не как
статистику, а как утверждение о раскладке — «слой × контекст». Восемнадцатый
проект, не являющийся ни слоем, ни контекстом, ломает не сборку, а правило,
по которому в этом реакторе заводят модули.

**Отдельный репозиторий фронтенда.** Отвергнуто без обсуждения: §10.2 обещает
один jar со статикой внутри, а инструмент для одной архитектурной практики
банка не окупает двух конвейеров и версионной вилки между ними.
