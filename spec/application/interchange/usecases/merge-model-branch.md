# UC-IXC-007 — Слияние предложения из ветки по сущностям

**Актор:** `ARCHITECT` · **Триггер:** архитектор указывает ветку предложения
(merge request), тег или голову ветки привязки, разошедшуюся с моделью ·
**Результат:** модель содержит правки обеих сторон новой версией; конфликты
разрешены архитектором по полям

Импорт по ссылке (`UC-IXC-006`) заменяет содержимое модели состоянием коммита
целиком: правки, сделанные в базе после развилки, теряются. Слияние их сохраняет.
Три состояния — общий предок, «наше» и «их» — сравниваются **по объектам
с идентификатором и их полям**, а не по строкам YAML (`INV-IXC-010`): построчное
слияние двух правок одного элемента даёт объект, которого никто не создавал.

## Предусловия

- У рабочего пространства есть рабочая привязка `GitBinding`; читается только
  репозиторий привязки с её учётными данными.
- У модели есть опубликованная версия (`git_sha`): от её коммита ищется общий предок.
- Модель видна актору на запись; для применения модель заблокирована им (`UC-MDL-005`).

## Три состояния

| Состояние | Откуда |
|---|---|
| «Наше» | Текущее содержимое модели в базе — то, что будет заменено (как в `UC-IXC-006`) |
| «Их» | Каталог модели в коммите ссылки |
| База | Каталог модели в общем предке (merge-base) коммита ссылки и коммита последней опубликованной версии модели |

Каталог модели находится по суффиксу `.<8 hex от ModelId>` и собирается в документ
тем же читателем, что восстанавливает снимок (`UC-IXC-003`).

## Правила слияния

Объект — модель, папка, элемент, связь, представление; ключ — `archiId`. Поля
объекта: каждый атрибут отдельно (`name`, `type`, `source`, `target`, …),
`documentation`, `properties` (список целиком — порядок значим), `raw_xml`, `folder`
(родительская папка), у представления — `diagram` (узлы и рёбра целиком).

| Ситуация | Разрешение |
|---|---|
| Поле изменено только в одной ветви | Берётся изменённое |
| Поле изменено в обеих одинаково | Берётся |
| Поле изменено в обеих по-разному | Конфликт по полю: выбор «наше» / «их» |
| Объект добавлен только в одной ветви | Добавляется |
| Объект добавлен в обеих с одним `archiId` | Сравнивается по полям, как изменённый от пустого |
| Объект удалён в одной ветви и не тронут в другой | Удаляется |
| Объект удалён в одной ветви и изменён в другой | Конфликт объекта: «удалить» / «оставить с правками» |
| Геометрия представления менялась в обеих ветвях | Конфликт поля `diagram`: представление целиком с одной стороны |
| Обе ветви вставляли в одну папку | Оба набора сохраняются, см. «Порядок» |
| Переименование или перенос объекта в одной ветви, правка других полей в другой | Не конфликт — ключ идентификатор, а не имя и не путь |

**Порядок детей** конфликтом не бывает. Основа — порядок той ветви, которая меняла
относительный порядок общих детей (не меняла ни одна — наш); добавленное другой
ветвью встаёт после всех соседей, стоявших перед ним в этой ветви.

**Каскад** — следствие разрешения, а не конфликт; каждая запись попадает в отчёт:

- связь, у которой не осталось источника или цели, удаляется — и связь на неё тоже;
- узел представления, ссылающийся на удалённый элемент или связь, удаляется вместе
  с вложенными узлами; ребро без концов удаляется, `targetConnections` очищается;
- две ветви переложили папки друг в друга — перенос из «их» откатывается.

## Основной сценарий

Два шага, как у импорта по ссылке: **отчёт** и **применение**.

### Шаг 1 — отчёт слияния

**Given** модель с опубликованной версией и ссылка на предложение

**When** архитектор запрашивает отчёт по ссылке; повторный запрос может нести
выборы по уже показанным конфликтам

**Then**
1. Ссылка разрешается, как в `UC-IXC-006`; находится общий предок и три состояния.
2. Слияние строится по правилам выше. Конфликт без выбора в отчёте разрешается
   в пользу «нашего» — чтобы показать результат, но не применить его.
3. Результат проверяется, как файл на импорте (`UC-IXC-001`): разбор и методология;
   находки — в отчёте, признак `applicable` ложен, если строгий режим отклонит
   применение или остались конфликты без выбора.
4. Отчёт несёт: конфликты с адресом `<archiId>:<поле>` (`<archiId>:*` — удаление
   против правки), значениями базы, «нашим» и «их» и сделанным выбором; каскад;
   изменения результата относительно текущего содержимого (как в `UC-IXC-006`);
   отметки для холста — объекты результата `ADDED`/`REMOVED`/`CHANGED` и по каждому
   изменённому представлению добавленные узлы с абсолютной геометрией.
5. В отчёте — `commitSha`, `mergeBaseSha` и `baseHash`: ими применение подтверждает,
   что применяет увиденное.
6. В базе ничего не меняется.

### Шаг 2 — применение

**Given** отчёт, выбор по каждому его конфликту и блокировка модели у актора

**When** архитектор применяет слияние с `commitSha`, `mergeBaseSha`, `baseHash`
и выборами из отчёта

**Then**
1. Читаются ровно коммиты отчёта; слияние строится заново с переданными выборами.
2. Сессия импорта с целевой моделью проходит `RECEIVED → PARSED → VALIDATED → APPLIED`
   (`INV-IXC-002`); источник — ссылка и коммит.
3. Одной транзакцией: содержимое модели заменяется результатом, фиксируется новая
   версия, версия встаёт в очередь публикации, слитый коммит записывается за моделью,
   сессия закрывается (`INV-IXC-012`).
4. Комментарий версии — переданный, иначе «Слияние из Git: ссылка (7 знаков коммита)».
5. После коммита транзакции публикуется `ImportApplied`.

## Слитый коммит и публикация

Слитый коммит записывается за моделью (последний — один). Публикация (`UC-IXC-003`)
учитывает его так:

- чужая правка каталога модели, входящая в слитый коммит, — **не** расхождение:
  архитектор её принял;
- слитого коммита нет в голове ветки — он становится **вторым родителем** нашего
  коммита. Ветка merge request'а становится предком ветки привязки, и merge request
  закрывается сам, без текстового слияния (`INV-IXC-009` — история не переписывается).

Слияние коммита, содержащего **голову ветки привязки**, разрешает расхождение, если очередь
публикации модели на нём стоит: открытые записи очереди старше новой версии закрываются
как пропущенные — новая версия их содержит; голова становится последним известным коммитом
привязки. Без расхождения очередь не трогается: старые версии публикуются своими коммитами. Если результат
совпал с текущим содержимым (выбрано всё «наше»), версии нет, но слитый коммит
записан — следующая версия ляжет поверх головы.

## Альтернативы и отказы

| Ситуация | Ответ | Поведение |
|---|---|---|
| Нет роли `ARCHITECT`/`ADMIN` | `403` `IXC_ACCESS_DENIED` | — |
| Модели нет или она скрыта списком доступа | `404` | — |
| У пространства нет рабочей привязки | `409` `IXC_GIT_NOT_BOUND` | — |
| Ссылка пуста или недопустима; выбор по конфликту, которого нет | `422` `IXC_INVALID_REQUEST` | — |
| Ссылка не найдена | `404` `IXC_GIT_REF_NOT_FOUND` | — |
| В коммите ссылки нет каталога модели | `404` `IXC_GIT_MODEL_NOT_IN_REF` | — |
| Нет опубликованной версии, общего предка или каталога модели в нём | `409` `IXC_GIT_NO_MERGE_BASE` | Сливать не с чем — импорт по ссылке (`UC-IXC-006`) |
| Репозиторий недоступен | `503` `IXC_GIT_UNREACHABLE` | Модель не тронута |
| Каталог одной из сторон не собирается в документ | отчёт: находки, `applicable = false`; применение — `422` `IXC_CORRUPT_DOCUMENT` | Сессия `REJECTED` |
| Остались конфликты без выбора | отчёт: `applicable = false`; применение — `422` `IXC_MERGE_CONFLICTS_UNRESOLVED` | Модель не тронута |
| Нарушения методологии результата в строгом режиме | отчёт: находки, `applicable = false`; применение — `422` `IXC_STRICT_IMPORT_REJECTED` | Сессия `REJECTED` |
| Содержимое модели изменилось после отчёта | `409` `INV-IXC-012` | Сессия `REJECTED`; нужен новый отчёт |
| Модель не заблокирована актором | `409` `INV-MDL-006` | Сессия `REJECTED`, модель не тронута |
| Результат совпадает с текущим содержимым | `200`, `created = false` | Версии нет, слитый коммит записан |

## Порты

**Входящие:** `PreviewModelMerge(modelId, ref, resolutions)` → `GitMergePreview`;
`MergeModelBranch(modelId, ref, commitSha, mergeBaseSha, baseHash, resolutions, comment?)`
→ `GitMergeResult`. Обе — операция `MergeModelBranch` в таблице ролей.

**Исходящие:**
- `GitRepositoryPort` — разрешение ссылки, общий предок, чтение каталога
- `GitYamlReader` — обратная сборка документов трёх состояний
- `ModelStates` — текущее содержимое модели и замена его новой версией
- `PublishedVersions` — коммит последней опубликованной версии
- `ModelMerges` — слитый коммит модели
- `ImportSessionRepository`, `GitOutbox`, `GitBindingRepository`
