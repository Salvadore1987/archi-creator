# spec/ — единственный источник истины

Этот каталог содержит формальную спецификацию системы **Archi Creator**
и с 2026-09-28 является её единственным нормативным источником. Код, тесты,
интеграционная документация и диаграммы — производные артефакты. Если спека
и код расходятся — фикс идёт в спеку, затем в код.

## Отношение к `docs/`

**Разворот 2026-09-28.** До этой даты `spec/` была производна от `docs/`,
а требования объявлялись в `docs/archi-creator.md` §2. Теперь наоборот.

| Каталог | Что это | Статус |
|---|---|---|
| `spec/` (этот) | Нормативная спецификация: реестр требований, якорные единицы (`INV-*`, `UC-*`, `UI-*`, `ADR-*`), машиночитаемые контракты | **Источник правды.** Расхождение с кодом — фикс в спеку, затем в код |
| [`docs/`](../docs/) | Обоснования и история: зачем так, какие варианты отвергнуты, обзор, развёртывание, этапы, журнал §13, макеты | Ненормативно. Отвечает на «почему», а не на «что» |

Направление зависимости: **`docs/` объясняет то, что `spec/` требует.**
Нормативный текст требования живёт в
[`product/requirements.yaml`](product/requirements.yaml);
`docs/archi-creator.md` §2 держит таблицу-индекс для навигации и ссылается сюда.

При расхождении прав `spec/`. Если правка по существу меняет решение, она идёт
в `spec/`, а обоснование дописывается в `docs/` — нормативным оно от этого
не становится.

Из `spec/` в `docs/` ведут ссылки на разборы: полсотни мест, где обоснование
уже написано, и переписывать его в спеку значило бы держать два текста об одном.
Целостность этих ссылок проверяет `tools/check-links.py`.

## Уровень строгости

Применяется **spec-anchored**: спека и код сосуществуют, синхронизация
двусторонняя. CI содержит gate, проверяющий соответствие кода доменной
модели спеки (см. раздел «Верификация»).

## Технологический контекст

- **Стек:** Java 25, Spring Boot 4.x (Web, Data JPA, Security OAuth2 Resource
  Server, Validation), PostgreSQL 16 + Flyway, Keycloak 26 (OIDC/JWT),
  StAX на чтение XML и детерминированный writer на запись, React 19 +
  TypeScript + Vite, React Flow, Apache Batik (растеризация), Anthropic API
  (`claude-sonnet-5`), JUnit 5 + Testcontainers + Playwright, Maven,
  Docker Compose. Брокера сообщений в стеке нет — см. «Публикация событий».
- **Маппинг слоёв на модули реализации:** отдельные Maven-модули.

| Слой спеки | Модуль | Зависимости |
|---|---|---|
| `domain/<bc>/` | `archi-<bc>-domain` | нет (чистый Java, без Spring) |
| `application/<bc>/` | `archi-<bc>-application` | `archi-<bc>-domain` |
| `contracts/<bc>/` | `archi-<bc>-adapter-rest` (генерация) | application |
| — (инфраструктура) | `archi-<bc>-adapter-persistence` | application |
| `nfr/<bc>.yaml` | `archi-bootstrap` | все модули, Spring Boot |

Граница «domain не знает о фреймворке» держится **сборкой**, а не соглашением:
у `archi-<bc>-domain` в `pom.xml` нет ни Spring, ни JPA, поэтому нарушение
не компилируется. Раскладка заведена 2026-09-29 (`ADR-0001`): 17 проектов
в реакторе, jar собирается в `archi-bootstrap/target/`. В шести модулях
(`domain` и `application` трёх контекстов) запрет подкреплён правилом
`maven-enforcer-plugin`.

## Публикация событий

Брокера в стеке нет, поэтому `publishing.pattern: direct` во всех
`domain/<bc>/events.yaml`: события публикуются в процессе после коммита
транзакции. У `direct` есть окно потери — событие может не дойти, если
процесс упадёт между коммитом и доставкой. Для текущих потребителей
(инвалидация кэша, уведомление UI) это допустимо; для Git-выгрузки на
этапе 7a — нет, и там потребуется `transactional_outbox`. Решение
не принято, ADR не заведён: см. «Незакрытые решения» ниже.

Файлы `contracts/<bc>/events.asyncapi.yaml` описывают **контракт полезной
нагрузки**, а не транспорт: `protocol: in-process`. Появление брокера
меняет в них только `servers` и `bindings`, схемы сообщений остаются.

│

Интерфейс живёт слоем, а не четвёртым bounded context'ом: у него нет агрегатов
и доменных событий, он проекция `modeling` ([`ui/README.md`](ui/README.md)).

## Bounded contexts

| BC | Код | Отвечает за | Этапы [§12](../docs/archi-creator.md#12-этапы-работ) |
|---|---|---|---|
| `modeling` | `MDL` | Модель как таковая: папки, элементы, связи, представления, блокировки, версии, валидация по метамодели | 2, 3, 4, 6 |
| `interchange` | `IXC` | Преобразования на границе: кодек `.archimate`, OEF, CSV, SVG/PNG, Git-выгрузка | 1, 5a, 6a, 7a–7c |
| `advisor` | `ADV` | ИИ-помощник: ревью, подсказка, план, документация; аудит и бюджет токенов | 5 |

Граница между `modeling` и `interchange` проходит по языку: `modeling`
говорит об элементах и связях, `interchange` — о файлах, узлах XML и
сохранности байтов. Lossless round-trip (NFR-05) — инвариант `interchange`,
а не `modeling`.

## Соглашения

**Идентификаторы атомов спеки.** Каждая атомарная единица получает
стабильный код, который не меняется при редактировании и не переиспользуется
при удалении. Типы якорей:

| Префикс | Значение | Пример |
|---|---|---|
| `INV-<BC>-NNN` | Бизнес-инвариант | `INV-MDL-001` |
| `UC-<BC>-NNN` | Use case | `UC-MDL-001` |
| `UI-NNN` | Правило интерфейса | `UI-012` |
| `ADR-NNNN` | Архитектурное решение | `ADR-0001` |
| `FR-NN` / `NFR-NN` | Требование — объявляется только в `product/requirements.yaml` | `FR-33` |

**Идентификаторы агрегатов** — двойные:

- **Внутренний ключ** — `UUIDv7`, генерируется на стороне приложения
  (не БД), монотонен по времени, используется как первичный ключ и во
  всех внутренних ссылках.
- **`archi_id`** — идентификатор объекта в файле Archi, формат
  `id-<24 hex>`. При импорте **сохраняется буквально и не
  перегенерируется**; новые объекты получают id в том же формате.
  Уникален в пределах модели: `UNIQUE (model_id, archi_id)`.

Два ключа нужны потому, что `archi_id` — внешний формат, уникальный только
внутри своего файла: две модели легально содержат один и тот же id.
Делать его первичным ключом означает тащить чужую схему именования в
ссылочную целостность. Подробности — [`docs/backend.md` §3.4](../docs/backend.md#34-кодек-archimate--ключевые-решения).

**Язык.** Проза и описания — на русском. Имена сущностей, полей, событий,
идентификаторы use case'ов, использующиеся в коде — на английском, чтобы
спека ложилась 1:1 на код без транслитераций.

**Референсы между файлами.** Используется формат
`domain/<bc>/aggregates.yaml#ArchitectureModel` или `events.yaml#ModelVersionCommitted`.
Это нужно для агентов, чтобы они могли находить связанные части без
семантического поиска.

**Версионирование.** Каждый файл имеет frontmatter с полями `version` и
`last_modified`. Изменение мажорной версии = breaking change, требующий
регенерации downstream-артефактов и обновления `adr/decisions.yaml`.

## Верификация

- **Статический:** ArchUnit-правила на направление зависимостей между
  слоями; при выбранном разделении на Maven-модули основная часть границ
  проверяется самой сборкой.
- **Контрактный:** генерация клиентов/серверов из `contracts/*.openapi.yaml`;
  contract-тесты против реализации.
- **Бизнес-правила:** каждый `INV-<BC>-NNN` из `invariants.md` имеет
  соответствующий тест (см. таблицу «Маппинг на тесты» в конце каждого
  `invariants.md`).
- **Round-trip:** golden-file тесты на `docs/Hamkorbank_AS_IS_strict.archimate`
  ([`docs/backend.md` §9.1](../docs/backend.md#91-golden-file-тесты-round-trip--критический-контур)).
  Регрессия блокирует сборку.
- **Целостность спеки** — два скрипта, оба возвращают ненулевой код при первом
  нарушении и годятся как gate в CI:

| Скрипт | Что проверяет |
|---|---|
| `tools/check-links.py` | Ссылки между файлами: существование файла и наличие якоря — и в markdown-ссылках, и в путях внутри прозы и YAML |
| `tools/check-traceability.py` | Каждое требование покрыто якорем; каждый якорь привязан к требованию; якоря объявлены по одному разу; ссылки на якоря разрешимы; инварианты связаны с use case'ами |

Известные пробелы объявляются полем `note` у требования и попадают в отчёт
как объявленные, а не как нарушения: скрытый пробел хуже описанного.

## Пайплайн генерации

Каталога `.claude/agents/` в репозитории пока нет — таблица ниже описывает
референсное разделение ответственности, к которому спека готова:

| Агент | Что читает | Что генерирует |
|---|---|---|
| coordinator | `product/`, `domain/bounded-contexts.yaml` | план задач, маршрутизация |
| code-generator | `domain/<bc>/`, `application/<bc>/`, `contracts/<bc>/` | модули реализации |
| test-generator | `application/<bc>/usecases/`, `invariants.md` | unit, integration, arch-тесты |
| docs-generator | `adr/decisions.yaml`, `application/<bc>/` | ADR (MADR), wiki-страницы |
| diagram-generator | `domain/<bc>/aggregates.yaml`, `contracts/<bc>/` | C4, sequence, ER |
| verifier | вся спека + сгенерированный код | отчёт о соответствии, gate в CI |

## Добавление нового bounded context

1. Зарегистрировать BC в `domain/bounded-contexts.yaml`.
2. Создать `product/<bc>.md`, `domain/<bc>/`, `application/<bc>/usecases/`,
   `contracts/<bc>/`, `nfr/<bc>.yaml`.
3. Заполнить минимально: ubiquitous language → aggregates → invariants →
   один use case.
4. Прогнать verifier-агента и статические проверки локально.

## Незакрытые решения

[`adr/decisions.yaml`](adr/decisions.yaml) содержит 15 решений: три оформлены
файлами MADR (`ADR-0001`…`ADR-0003`), двенадцать проиндексированы из журнала
§13 со ссылкой на уже написанное обоснование.

Открытым остаётся одно:

- **`ADR-0003`, механизм публикации событий** — статус `proposed`. `direct`
  выбран как временное состояние и для Git-выгрузки этапа 7a не годится: окно
  потери события ломает правило очистки снимков версий. Решение принимается
  при открытии этапа 7a, чтобы не заводить outbox за шесть этапов до его
  первого потребителя.

Пробелы в покрытии — объявленные и отслеживаемые:

- **FR-29 (ACL на уровне модели)** — ни инварианта, ни use case'а: механизм
  в спеке не описан.
- **NFR-03 (p95 ≤ 300 мс)** — проверяется нагрузочным профилем, а не якорем.
- **`INV-IXC-006`, `INV-IXC-010`, `INV-IXC-012`** — без use case'а: их сценарии
  относятся к этапам 6a, 7c и 7b.

## Что НЕ кладём в спеку

- Реализационные детали (имена классов сервисов, инъекции, структура
  пакетов).
- Конкретный SQL, кроме миграций контрактного характера.
- Логи, диагностические сообщения.
- Стиль кода — это в `.editorconfig` и стандарте разработки.

Спека описывает **намерение и контракт**, не реализацию.
